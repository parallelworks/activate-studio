### Quick start

Files collect in many folders, drives, and systems. Finding one means remembering where it was saved, and answering a question from a set of documents means opening them one at a time.

Studio indexes your folders with GUFI. **Search** finds files by name, by the words inside them (PDFs and office documents, and text in images and scanned pages where OCR is available, as it is in the macOS app), and by meaning. **Query** answers questions about the files themselves, such as the largest, the newest, or the totals by type. <!-- ai -->**Chat** answers questions from the files and links each source it used.<!-- /ai -->

Files stay where they are. Studio keeps its index in a folder of its own, reads each file in place, and follows the file system's permissions. Indexing, search, and query run where Studio runs and need no network connection.<!-- ai --> Chat sends text only to the model endpoint you configure, which can be on the same computer.<!-- /ai --> The same index works for a folder on a laptop and for a cluster's file systems.

1. **Choose a folder.** On a computer of its own, setup asks which folder to index; Settings, Indexing, Libraries changes it later.
2. **Search.** Type a word or phrase in **Search**, then click a result to open the file at the match.
3. <!-- ai -->**Ask.** Open **Chat** and ask in plain language. The answer links the files it used.<!-- /ai -->
4. **Query.** Open **Query** and pick a preset, or build one, to list files by size, age, type, owner, or label.

On a computer of its own, setup can be run again at any time, starting from what is set now: **Run setup again** in Settings, General, or **Run Setup…** in the macOS app's menu.

On Linux, the app is installed for one user with no administrator rights (`install.sh` from the unpacked archive), or for everyone by an administrator with a `.deb` or `.rpm` package. It opens in its own window where WebKitGTK is installed, with the system folder chooser for **Choose another folder…**, and in the default browser where it is not (then `activate-studio --stop` stops it). Run `activate-studio --uninstall` to remove a per-user install; your documents are never removed. See `docs/LINUX-APP.md`.

On Windows, the Linux app runs inside WSL2 (Windows Subsystem for Linux): in its own window on the Windows desktop, or with `activate-studio --browser` in a Windows browser. Windows folders are under `/mnt/c`, and a Windows path such as `C:\Users\me\Documents` can be typed wherever a folder is asked for. Labels on files in Windows folders are kept by Studio, and changes made in Windows are found by the background sync. See `docs/WINDOWS.md`.

The macOS app needs no administrator rights. Opened from its disk image, it offers to install itself in Applications in your home folder (`~/Applications`), where it updates itself. An administrator can put it in `/Applications` instead; that copy updates itself only for users who can write there. On a Mac that does not allow the app's background item (a LaunchAgent), the app starts its server itself when it opens, instead of at login.

# Basics

## Chat

Ask in plain language. The assistant searches the knowledge base, reads the files that matter, and links each source; a source link opens the file in the Library, in the library it came from. Past conversations are kept in the Studio. A chat goes into a library only when you save it, and a saved chat is searchable like any other file.

- **Attach** files or images with **+**, then **Add files**; they are added to the library and indexed.
- **+**, then **Tools**, switches kinds of tools on or off for your chats: the knowledge base, platform workflows, platform changes, agents, editing the library, transfers, extensions, and each attached MCP server. Switch off workflows to keep a chat from launching anything, or editing to keep it read only. A dot on **+** means something is off; the choice is kept in this browser. A Studio with no platform connected (no ACTIVATE credential and no pw CLI sign-in) offers only the library tools, and the platform switches are not shown.
- **Scope**, at the top right, chooses which libraries the assistant searches in this chat and limits answers to material with the labels you choose. With more than one library, the chat searches **All libraries** until you untick some; tick any of them, or **All libraries** for every one, and at least one stays ticked. The button names the one library chosen, **All libraries**, or how many are ticked. The choice is kept in this browser.
- **pw code** or **Studio**, at the top right, chooses what answers the chat. Where the Studio runs under ACTIVATE and pw code can be reached, pw code answers by default: the ACTIVATE agent harness, in a pw code session of yours that searches and reads these libraries with the Studio's tools, works in files, and runs the commands you approve. Elsewhere, or when you choose it, the Studio assistant answers with the Studio's own tools and the model chosen under the message box. A Studio that does not run under ACTIVATE always answers with the Studio assistant and shows no pw code choice. pw code gets the Studio's own tools, the ones the Studio assistant uses: search and statistics from the index across the libraries, reading files, writing reports and other files into the library, labels, and platform workflows. Those that only read run without asking, those that write ask first, and kinds of tools you switched off under **+**, then **Tools**, stay off. Deletes, cluster changes and transfers stay with the Studio assistant. Before each message the Studio checks that the session has the tools, and reconnects them or starts a new session when it does not; the menu says whether the chat's session has them. If pw code cannot reach them, the Studio assistant answers that message, the chat says why, and the Studio assistant answers by default for the next ten minutes. Each conversation keeps its own choice in this browser, and switching keeps the conversation: pw code is given the turns it did not see, and the Studio assistant reads them all. pw code answers with its own model, which the menu names once pw code has answered. On a Studio several people share, pw code runs as you once you sign in with ACTIVATE under Settings, Model access, and works in your own space when you have one.
- When pw code asks to run a command, or has a plan for you to approve, a bar over the message box shows it with **Allow** and **Deny**. You can answer there or in PW Code on the web, and the bar leaves when either answers. **Open this chat in PW Code on the web**, in the same menu, opens the session in ACTIVATE, where you can follow it and keep working in it. A chat that continues a session from the Code page links back to it there from the same menu. Escape interrupts pw code's turn. If the page reloads or loses its connection while pw code works, the turn runs on, the bar comes back for anything it asks, and the reply shows when it ends.
- Type **/** to pick a skill, a tool, or a persona to use. With pw code answering, a persona puts the chat's session in `agents/<persona>` of your library, with the persona in that folder's `AGENTS.md`.
- Type **@** to point the assistant at a library file. The list starts at the top folder of the chat's library (the knowledge base when it is among those ticked) and narrows by file name as you type; choosing a folder opens it, and choosing a file writes `@[path]` into your message. The assistant gets that file's text with your question, and in the sent message the name is a link that opens the file.
- **Effort**, beside the model, sets how long the model reasons before it answers. **Default** leaves it to the model; **Low**, **Medium**, **High** and **Max** ask for less or more. Each conversation keeps its own, and a new chat starts with the last one you chose. A model that takes no effort setting answers as it always does.
- Ask it to save something in the library: a note or script as text, a report as a PDF or Word document (with images from the library, such as a screenshot you attached, placed where the report names them and scaled to the page; ask for a cover page, left-aligned text, landscape pages, a font such as Times New Roman, a text size, margins, line spacing, a page break, or a line of text at the top or bottom of every page such as a document marking, and it sets them; pages are numbered, footnotes are numbered and listed under Notes at the end, and a checklist shows checked and empty boxes), a table as an Excel workbook (a sheet per table, numbers as numbers, the header row kept in view). Tables are fitted to the page without splitting words; when a table has too many columns to fit, or the PDF's font lacks a character (some symbols and emoji), the assistant is told and says so, and can turn the page to landscape or split the table. It writes the file, indexes it, and links it; a file that exists is replaced only when you say so. Slides are not made; ask for a PDF or Word document with a heading per slide.
- Reports follow common document conventions. Body text is justified and black, sections are separated by their headings with no divider lines, and a paragraph that opens with a label shows it in italic with a colon (*Why now:* the contract ends in March), whether the assistant wrote it in bold or with a period; a key and its value, such as **Date:** 14 November 2026, keep their form. A cover page holds what comes before the first page break, centered, with no page number, and the pages after it are numbered from 1, in the PDF and in Word and Google Docs alike. There is no written table of contents: Word and Google Docs make one from the headings. When the assistant saves a report it is told what a check of the writing found (dashes used as punctuation, intensifiers such as "truly", sentences written twice, and the length of long reports), and it revises where the advice applies. Your library's conventions file, when it has one, sets its own style, such as the font for a kind of document, and comes first.
- Ask for a report in more than one format ("save it as Markdown, PDF and Word") and it writes the report once, as a Markdown file, and makes the PDF and the Word document from that file, beside it and under its name. Ask for a change afterwards ("change the title", "add a row for the fifth rack", "drop the last section") and it edits the Markdown where the change is and makes the PDF and the Word document again, in seconds: the report is not written out again. A PDF or Word document you have replaced with your own since is left as it is. The same goes for any text file in the library: a note, a script or a case file is changed in place, and the answer says what changed.
- Ask it to move, rename, copy or delete files in the library. Moves, renames and copies run at once, inside the main library, and never replace a file: a name already taken is skipped or refused, and a copy into the same folder is named "copy". A delete asks first: the chat lists the files and waits for **Yes, allow this call**, and the Studio cannot undo it. Only files are deleted, never folders. Copying or moving files to another library or system is a transfer (see Transfers).
- Ask it to run work on a connected HPC system; it follows the run and explains a failure if there is one. A side view beside the chat shows the run: its form as submitted, the live graph of its jobs, and the web session it opens, such as a study viewer. Click a step in the graph to read its summary, its log as it grows, and the script it ran. **Beside chat** on a session card adds the session as a tab there, **Full screen** shows it over the whole Studio (Close or Escape returns), and **Pop out** opens a tab in a window beside the Studio.
- Ask to see running sessions by a word or a run ("show me the modo sessions"); each comes back as a card that opens it.
- Ask what storage you have, or ask it to start, resume, stop, or destroy a cloud cluster or cancel a workflow run. Each of these changes asks first: the chat shows the exact call and waits. **Yes, allow this call** runs it, **No, deny this call** does not, and when stopping or destroying a cluster you can choose the other instead. A request left unanswered for 30 minutes expires. Only the person who asked can answer, and the change runs with their own platform key.
- **Select chats**, above New chat, deletes old conversations together.
- **Download**, in a conversation's menu in the list, saves it as a Markdown file. A notice says where it went: the folder in the Linux and Windows app, Downloads in the macOS app, or your browser's downloads folder; if it cannot be saved, the notice says why. Export CSV in Search and Query shows the same notice.
- **Save**, at the top right of an open chat, saves a copy of it as a Markdown file in `chat-sessions/` of your own space when you have one, where only you can read it, or of the main library otherwise. Before it writes anything it says where the copy goes and who can read it there. Saving again replaces the copy, and deleting the chat leaves the copy in the library. You can also ask the assistant to save or remember the chat; it does the same and says where the copy went.
- **Model access**, at the foot of the conversations list, opens the Settings page for models and keys.
- In a shared session, add your own model key under Settings, "Model access", to chat as yourself.
- A reply with no answer says why: the model reasoned without answering, ran tools without answering, or returned an empty reply, which some providers do when they decline a request. A provider that is rate limiting is retried twice after short waits. Either way the reply ends with **Retry with** links to the other models; nothing is sent to another model until you click one.
- Send a message while a reply is running to steer it: the reply takes it in at its next step and shows "You added" where it did. A message sent while the reply is writing its final answer goes out after it, as before.
- A message whose reply was cut off, for example when the Studio restarted, says so and offers **Retry**, which sends it again.
- While a reply streams, its thinking and tool calls stay folded to one line each; click one to open it.
- A message sent while a reply streams, with or without attachments, waits under the reply and goes when it finishes. Escape stops the reply while the chat is on screen. Opening an attachment or a file from the chat, and pressing Escape on the page that shows it, leaves the reply running and the waiting messages in place.
- Ctrl+F (⌘F on a Mac) finds text in the open conversation. Each match is tinted and the bar counts them; Enter and Shift+Enter, the arrow keys, or Ctrl+G and Shift+Ctrl+G (⌘G and Shift+⌘G) step through them, and the search follows a reply as it streams. Escape closes the bar. On the other pages, the key is left to the page or the browser.
- The assistant has separate tools for a file: search finds it, **read_kb_file** returns the text the index holds for it (so it works even when the file itself cannot be reached, and it says where the text came from), and **read_original** opens the file itself. For a library on a host that only runs the index, you can name another host that has the files, such as a file transfer host (Settings, Indexing, Libraries, **Originals via**), and **read_original** tries it, over ssh as you, when the library's own host cannot give the file. When no host has the file, the assistant is told which were tried and says so.
- A reply's finished tool calls fold into one row, such as "Ran 3 searches, read 2 files"; click it to see each call. A running call and a failed one keep their own rows. When the assistant searches, queries, or lists a folder, open that call's row for **GUFI command**, the commands it ran, ready to copy, as Search does. Only you see them, and the model does not receive them.

## Library

The folder tree beside a viewer. Markdown, code, CSV and TSV tables, images, PDFs, office documents, and STL and STEP models open in place.

- With more than one library, the switcher above the tree names each with what you may do in it: **Read/write**, **Read only** or **Shared** (a folder someone shared with you), and **(on** a system**)** for one on a cluster or host, such as "Runs · Read only (on cluster-a)". Search, Query and Settings, Indexing, Libraries name them the same way.

- **+ Add** takes files or a whole folder, by dropping them or with **Choose a folder**; folders keep their structure, and names that start with a dot are left out. One file can be up to 200 MB; a larger one is named as failed and the rest go up. Drop onto a folder in the tree to add there. Each upload, move, copy and delete has its own row below the tree with its progress, and more can be added while one runs: uploads wait their turn, and you can leave the page and come back.
- The arrow beside **+ Add** opens a menu: **Add files…** opens the same panel as **+ Add**; **Add a library…** opens the Add a library form from Settings in a dialog; **Import a library list…** opens the import in a dialog, where you choose the file, paste the list, or drop the file onto the dialog. When every ticked library is added, the dialog closes and the new libraries are in the picker at the top of the tree. If one fails, the dialog stays open with the reason. The arrow is shown only to someone who may add libraries: anyone on a Studio without sign-in, and, where people sign in, someone who can add libraries of their own over pw ssh or through the platform's index workflow.
- **Add a library**, **A system**, **My own folder** (My library, Preview) makes a folder of your own on the system chosen, `~/studio` unless you choose another, closed to other accounts and indexed as you. **System** lists your clusters on the platform, the Studio's own cluster first when it has one, and **Another system…** takes a name; on a Studio only you use with sign-in off, **A host over ssh…** takes a user@host reached with your own keys. You can upload, add folders, rename, move and delete in it from the Library, and its index catches up about 20 seconds after the last change, including after a transfer into it. A folder you opened in the last two minutes shows at once and is read again behind it, so a change made on the cluster outside the Studio shows the next time you open the folder. **Share…**, on a right-click of a folder in it, gives an account, a group you are in, or every account read, or read and write, on that folder. The Studio sets it as you with POSIX ACLs, and **Stop sharing** takes it back. The people you share with find it under **Add a library**, **A system**, listed for that system, and their copy is indexed and read as them. On a host over ssh there is nobody else on the Studio to share with, so **Share…** is not offered there. A cluster needs your ACTIVATE sign-in, which the Studio uses to reach it as you: without one, the form offers **Sign in with ACTIVATE** in place, and if the platform refuses your credential later, it says so and offers it again. Details are in `docs/MULTI-USER.md`.
- A library list file dropped onto the Library page is read as a list, not added as a file: the import opens with its libraries, and **Add the file to the library instead** adds it as a file. Studio checks the file with the server first, so any other `.json` file is added as before. This applies only where the arrow beside **+ Add** is shown, and not to files dropped from a file manager onto the Linux app's window, which are always added as files.
- The eye button above the tree shows hidden files and folders, those whose names start with a dot, and remembers your choice. Tool folders such as `.git` and `.cache` stay out of the tree either way.
- A library you built on one of your systems, under **Add a library**, **A system**, **Index a folder**, is yours to change too: upload, add folders, rename, move and delete run there as your account, and the system's permissions decide what you may change. Its index catches up about 20 seconds after the last change. An index you connected as it is stays read only.
- **Right-click** a file or folder to label it, add a folder, or delete it. In a read-only library the actions that would change it are shown disabled, with the reason on hover; labels still apply.
- **Right-click** a file or folder, or a selection, and choose **Copy to another library…** to copy it into another library, such as your own My library, when the Transfers page is on. It opens the Transfers dialog with a writable library chosen as the destination: pick the folder, and the plan shows what will be copied and how before anything starts. It only copies; the originals stay where they are. The copy is written as you, so it is yours and follows the permissions where it lands, and the destination's index shows it when that library is next indexed.
- With **All libraries** chosen, drag a file or folder onto a folder of another library to copy it there the same way: the dialog opens on the folder you dropped on. While you drag, folders that take the drop are marked, and folders of a library you cannot write in are dimmed with a not-allowed cursor. A drag within one library still moves, and a read-only library's rows drag only as a copy. **Paste** of a cut or copied item into another library is a copy too, so nothing leaves the library it was in, and so is a copy inside My library.
- **Right-click** a file and choose **Download** to save it to your computer without opening it. On a folder, **Download as zip** saves a zip of the files the Library shows in it, with its subfolders; files whose names start with a dot, and build and cache folders the Library leaves out, are left out of the zip too, and a link to somewhere outside the folder is not followed. A notice gives the number of files and the size as the download starts. A folder of more than 50,000 files or 8 GB (500 files or 1 GB in a library on another system, whose files are fetched one at a time) is refused with a notice, so download the folders inside it instead. **Upload files…** and **Upload a folder…** on a folder add files from your computer into that folder, a folder keeping its structure, with progress below the tree as for **+ Add**. In the app window the download goes to your Downloads folder.
- An HTML page shows on its **Page** tab with its scripts running in a sandbox that reaches nothing outside the page. **Print**, in the viewer's header, opens it in a tab of its own with the print dialog, where Save as PDF is one of the destinations; a print button on the page itself works too.
- **Find**, in the viewer's header, searches the open file. A file opened from a search result found by its words opens with Find set to those words; one found only by its meaning, name or folder opens without it. Punctuation inside a word matches any punctuation or space, as search reads it, so NIST_SP811 finds "NIST SP811".
- **Indexed text** shows what search sees for a file, including text read from images. Text longer than about 60,000 characters, such as a long manual's, is shown as plain text so it opens quickly.
- A CSV or TSV file opens on its **Table**: the header row and row numbers stay in view while it scrolls, a click on a column sorts it (numbers as numbers), and **Filter rows** keeps the rows that hold its text. Long values wrap in their cell. **Source** shows the file as written.
- A PDF opens on its **Pages**, and an Office file on its **Slides**, **Document** or **Sheets**. The pages are drawn by poppler where it is installed, and otherwise, as in the macOS app, by the viewer itself. Each page shows as a sheet on a gray backdrop, apart from the next, so its margins and page breaks read as they print. A PDF neither can draw shows its text and says why. Where LibreOffice is not installed, as in the macOS app, a Word, PowerPoint or Excel file (or an OpenDocument one) shows the text and pictures read from it, slide by slide or sheet by sheet, without its layout; a 97-2003 file (.doc, .ppt, .xls) opens on its indexed text.
- Zoom in on a PDF's or Office file's pages, or on an image, with **+** and **-** in the viewer's header, or hold Ctrl (Cmd on a Mac) and scroll, or pinch on a trackpad. Only the document grows; the rest of the Studio keeps its size, and the page scrolls across as well as down. The percentage between the buttons is the zoom, where 100% fits the pane's width; click it to fit again. With the document clicked, the + and - keys zoom it and 0 fits it. A zoom from the wheel or a pinch keeps the spot under the pointer where it is. Pages zoomed in are drawn again at a finer resolution, so text stays sharp up to 400%. Each file keeps its zoom while the Studio is open. The window's own zoom (Cmd+ and Cmd- in the macOS app, Ctrl+ and Ctrl- elsewhere) still zooms everything.
- If a file is moved, renamed or deleted while it is open, the viewer says so in place of the preview. A PDF or page rewritten while it is open, by the assistant or by anyone else, shows as it is now, with the pages it has. A picture or page in a chat reply whose file has since gone shows a short note in its place.
- An email, an Apple Mail message (`.emlx`) or an `.eml` file, opens as its message: Subject, From, To, Cc and Date, the body as text, and the names of its attachments. In a library built from a Mac's `~/Library/Mail` folder the messages keep Mail's numeric file names.
- If several libraries are available, the picker at the top of the tree switches between them. Each library on another system is named with the system it is on, as "(on cluster-name)"; on a Studio that runs on a cluster, the knowledge base and other folders on its own server are named with that cluster too. **All libraries**, the default, shows them as one tree, a folder each; Stats then covers all of them, and files can still be added and changed inside the knowledge base's folder. Each tab remembers its own choice. Search and Query have pickers of their own, where any of the libraries can be ticked.
- With the status panel open, the **Details** card describes what you last clicked in the tree, or the library itself: its size, files and folders, the latest change, the file types taking the most space, its labels and those inside it, and which library and index it comes from. For a library on a remote system it shows the file and folder counts from its connection test; **Count size and types** reads the whole index there, which can take minutes on a large one.
- Settings, Indexing, Libraries lists every library Studio searches, with where it is, its state, and what it can search. On a library whose files are not on the host that holds its index, **Originals via**, **Set**, names another host over SSH that has them (a user@host or a Host from your ~/.ssh/config, and the library's folder there if its path differs); **Test connection** checks it before **Save**. The Library viewer's file text and download, and the assistant's **read_original**, try the library's own location first and then that host. **Add a library** is one form, the same here and in the Library's Add menu, offering only what you may do. **Where**: **This computer** (on a Studio without sign-in; with sign-in, the libraries on this computer are the deployment's), **A system**, or **A bucket**. For a system, **System** lists your clusters on the platform, the Studio's own cluster first and running ones next, with **Another system…** to type a name and, on a Studio only you use, **A host over ssh…**. The form then says whose account reads it: on a system, always yours, with your ACTIVATE sign-in or your own ssh keys, never the Studio's. **What**: **My own folder** (My library, below), **Index a folder** there, read and written as you where your account may write, with **Build with** **pw ssh** or a platform **Workflow job** where the platform hosts the Studio, or **Connect an index** that is there already, which stays read only. Folders others shared with you on that system are listed under it, each with **Add**. On this computer, a folder or an index is read with the Studio's account and is read only. **Transfers**, **Keep a local copy and index it…** keeps a copy of a folder from a Transfers location, such as an SFTP or ssh host, a cluster or an rclone remote, on this computer and indexes the copy. It is the way to search a host account that allows SFTP only, such as an upload drop, and Add a library points there. Choose the location, open the folder to copy, and choose how often Studio looks for changes: every 15 minutes to begin with, or only when you ask. The row says when it last looked and what it brought, with a link to that transfer, and **Update now** looks at once. The copy takes as much space on this computer as the folder holds, and it is read only: put files in the location itself, and they arrive at the next look. Removing it deletes the copy and never the files at the location. Copies are offered only on a Studio without sign-in. **A bucket** (Preview) indexes a bucket, or a folder in one, of an rclone remote: any S3 compatible store, AWS or on premises, or another store rclone lists. Studio lists it with one fast list, about one request per 1,000 objects, and indexes each object's name, size and time without reading any object, so search, Stats and the Library tree work on it. Its row shows how many objects and how much data it holds, the requests a listing takes and, on AWS, what they cost at S3 Standard prices. It is listed again once a day to begin with, or every hour, every 6 hours, or only when you ask, and **List again** lists it at once. Opening a file reads that object alone: the first 512 KB of a text file, or the whole object up to 50 MB for a download or a document preview. **Read text** reads the text inside the objects too, so search finds them by their words: text files and documents (PDF, Office, OpenDocument, mail) up to 100 MB each, read on this computer. It is off until you choose **After each listing**, which first says how many objects it would read and how much data, what that costs (on AWS, data out and requests at S3 Standard prices; a store on premises charges nothing) and about how long it takes. The first pass reads each object once, one request each, and the row shows its progress, with **Stop reading** to stop; the next pass goes on from there. After that, each listing reads only the objects that are new or changed, and the text of an object that is gone leaves the index. Choosing **Off** stops reading; the text already read stays searchable. Images are not read for text yet. Buckets are offered only on a Studio without sign-in, and removing one deletes its index and never the objects. A build checks GUFI and the folders first, asks before making a folder that does not exist, and shows its progress in the list. A folder on this computer is kept in step as it changes. On a computer of its own, building a folder here offers suggested folders, also in setup: Documents, Desktop and Downloads where they exist (on Linux, where the XDG user folders put them), and on macOS Apple Mail's folder, which macOS lets the app read only with Full Disk Access (the suggestion opens that setting). A suggestion fills in the folder and its name and checks it, so **Build the index** finishes it; a folder already searched is not suggested. On a computer of its own, the main folder's row changes the folder, builds or updates its index, stops a build, deletes the index (never the files), and shows the index log.
- A library list is a file that sets up libraries in another Studio, such as one an administrator shares so each person connects the same indexes as themselves. **Export…**, beside Add a library, saves the libraries you tick as a `.studio-libraries.json` file in your downloads: where each one is and how it is built, and no keys, passwords, tokens or settings. The main folder is in it only when ticked, as a folder to index. **Leave out the user name**, on by default, writes a host over ssh without your user name, so each person connects with their own login and their own permissions apply. A library Studio built here goes in the file as its folder, for each person's Studio to index again; tick **Share the indexes built here** to have each person connect to this index instead and search it as themselves, which suits an index an administrator built as root. **Import…**, **Import a library list from a file…** in Add a library, and **Import a library list…** in the Library's Add menu read such a file, chosen, pasted, or dropped onto the dialog, and list each library with what it is, where it points, and a tick. One already here, one that cannot be read, and one this Studio cannot add (a folder to index here, or a library over ssh, where people sign in) show why and have no tick. A library over ssh has **Connect as**, your login name here when the file names none. Each ticked library is then checked and added as Add a library adds it, and its line says Added, Failed with the reason, or Skipped.

## Transfers

Transfers copies, moves and syncs files between the places Studio can reach, and lists every transfer with its progress. **New transfer** shows two locations side by side. Select files or folders on one side and press the **Start** button pointing to the other. Each side lists names with their size and modification time; on a narrow side, as with the Status pane open, the time and then the size are left out so the names keep their room. Once a transfer starts, the page goes back to the list with that transfer's details open beside it. A transfer runs on its own while Studio is running, so you can close its details, start another, or use other pages. **Back to activity** above the two sides, or **Transfers** in the navigation, returns to the list. **Transfers** in the navigation shows how many transfers are under way, and a red dot for a failure in the last day that you have not seen. The dot clears when you open the Transfers page or that transfer's details, or when a later run of the same transfer succeeds.

A location is a library (marked **Indexed** when it has an index, so its files are searchable), a folder on this computer, one of your clusters on ACTIVATE, a folder on another computer over ssh (a saved location, or the home folder of a computer a library is on), a remote of your rclone configuration (such as an S3 bucket or a cloud drive), or CONDUIT where a site runs it. A read-only location can be a source but not a destination, and nothing can be moved out of it.

A library is writable for transfers when Studio can reach its files with write access: the main folder, a library folder on this computer, a library on another computer reached with your own key or ssh login, or the computer its originals are read from. The file system's permissions decide. With sign-in on, a library folder on this computer other than the main folder is read only, since Studio would write there with its own account, not yours. Before a transfer is offered, Studio checks that it can write in the destination folder, and for a move in the folders the files leave; if it cannot, the plan says which folder and where. On an object store such as S3 it writes and deletes an empty test object, so a bucket you can only read is refused before the transfer starts.

When you choose a library that is read only, or whose files Studio cannot reach, its side of the page says why. With sign-in off it offers **Save a location for its files…**: the same dialog as Settings, Transfers, filled in with the host and folder Studio knows for that library, and empty where it does not know them. If you can reach that folder over ssh, this gives Transfers a place it can write. Studio tests the connection before saving, and the side then switches to the new location. **Save a location…** at the end of each side's location list opens the dialog empty. With sign-in on, saved locations are off, and the side says what can be written instead, such as your clusters reached with your own key.

- **Copy** puts the selection in the destination folder. A name that already exists there stops the plan unless **Replace files that already exist at the destination** is ticked.
- **Move** copies, checks the copy, and only then removes the originals.
- **Sync** makes the destination folder match one source folder by sending new and changed files. It deletes nothing unless **Delete files at the destination that are not in the source** is ticked, and then the plan lists every deletion.

Every transfer is confirmed. **Start** shows the plan: what goes where, the file count and size, what is replaced or deleted, and how the files move: rsync where both ends have it, rclone where one end is an rclone remote, otherwise Studio's own copy over ssh or SFTP, or CONDUIT. Files land in a staging folder and take their names only after Studio checks the count and sizes. A transfer into or out of the main library is indexed when it finishes. The Library tree, its details, Stats and the file count under the navigation show the change within about 15 seconds, whichever page is open and wherever the transfer was started; open folders and the selection stay as they were. A search run after that finds the files where they now are. Any other library's index shows the change after its next refresh: the plan and the finished transfer say when, such as after its next rebuild in Settings, Indexing, Libraries, or after the index is rebuilt where it is built.

Settings, Transfers shows what is ready with no setup. **Add a location** there asks for a name, a host (user@host, or a name from your ssh config) and a folder, and tests the connection before saving. The Transfers page opens the same dialog, and its message after saving says what the test found, such as whether rsync is there or the account takes SFTP only.

Saved locations and folders on this computer save as soon as you add, edit, remove or switch one, with a short message. How files move, library hosts and the defaults save with **Save**, and **Unsaved changes** shows beside it until you do. A switch changed there takes effect on Save, and its line says **Turns on when you save** or **Turns off when you save** until then; a mover's program field stays in place, unavailable while the mover is off. The page reads the settings again each time you open it and when the Studio window comes back into focus, so a location saved from the Transfers page or by the assistant shows up there. If the settings changed somewhere else after the page loaded, Save does not write over them: your changes are added on top, and the message says what changed. If the other change was to the same setting you edited, nothing is saved and the page says so; **Save** again keeps your version, and **Reload** shows the saved settings instead.

A host account that allows SFTP only, such as an upload drop, works as a location with no extra setup, and its folder can be searched as a library with **Keep a local copy and index it…** at the top of this page; that library's updates show in this list as started by Studio. Studio finds this on first use and reaches it over SFTP with the same ssh settings. Transfers to and from it use Studio's own copy, since rsync cannot run there, and the connection test says the account takes SFTP only. Checking a move or the **checksum** option reads each file back over the network, which takes longer on large files. It also sets the folders on this computer that transfers may use, and the defaults.

Studio uses the rsync installed on each end, and the two ends can run different versions. Copies within this computer and sends to a host work with rsync 2.6.9 and later, including the rsync 2.6.9 or openrsync that macOS ships. Pulling from a host needs rsync 3.2.5 or later on this computer, or a build that carries the fix for CVE-2022-29154, a flaw that lets the sending host write files outside the destination folder. Without it, Studio's own copy carries pulls and the plan says so. On a Mac, Studio also looks for Homebrew's rsync (`brew install rsync`) and uses it when it can do more. Settings, Transfers shows the rsync found, its version and what it is used for, and a connection test says the same of a host's rsync. A program path set there is always used as it is. If rsync cannot open its connection to the other end and nothing has moved yet, the transfer goes on with Studio's own copy, and its details say why, with what ssh or pw ssh reported.

Studio uses the rclone installed on your computer and its existing configuration, and never changes either. Each remote you set up with `rclone config` appears as a location, and Settings, Transfers shows the version found and the remotes with their types, or says plainly that rclone is missing or has no remotes. rclone moves files between a remote and this computer, or between two remotes; between a remote and a cluster or ssh host, Studio's own copy is used. Listings ask an object store for its listing only, so they are fast, and the times shown there are upload times. A sync with a remote compares size and a hash both ends have (such as MD5), and size and modification time where they share none. On an object store such as S3, rclone writes files straight to their names: each file appears only once whole, and Studio checks every file before it removes originals or deletes anything, but if the transfer fails, the files already sent stay there. rclone remotes are offered only with sign-in off.

With sign-in on, each person sees only their own transfers and reaches clusters with their own key, and the operator sets these settings.

A transfer can also start from Search or Query: tick results and press **Transfer…**. The dialog says how many items there are and in which libraries, and offers **Copy** or **Move**, a destination chosen with the same location list and folder browsing as one side of this page, and **Replace files that already exist at the destination**. The destination starts at a place that takes files other than the libraries the items are in, a place other than a library first, such as a folder on this computer; with none, choose one. **Continue** plans the transfer and shows the plan to confirm, as **Start** does here. If a plan is refused, such as when a file is already in the destination folder, the dialog scrolls to the reason. A transfer reads from one location, so a selection in several libraries makes one transfer per library, and their plans are confirmed one at a time ("1 of 2"); **Cancel** on a plan stops the ones after it. A library whose files Studio cannot reach is left out, and the dialog says so before **Continue**. A move out of a read-only library is refused, with **Copy instead**. One transfer that starts shows a notice with **Open in Transfers**, which opens it here; several show one notice, such as "2 transfers started", with **Open Transfers**, which opens this list. The page you started from stays open with its results, and the selection clears.

## Search

One box searches four ways, and each result says how it was found: **name** (any part of a file's name), **folder** (a folder it is in has the search in its name), **words** (whole words inside files: PDFs, office documents, notes, code, and text in images), and **meaning** (passages that say the same thing in other words, so a plain question finds a report that never uses its words). Hover the label to see every way a result was found. The line under the box says which libraries are searched by meaning; **How search works** explains each kind.

What a search can find in a library depends on its **index depth**, a scale of five stops, each adding to the one before and taking longer to index: **Names**; **Text** (the words inside files); **Text + OCR** (text in images and scanned pages); **Meaning on documents** (search by meaning over the first few passages of PDF, Office, text, Markdown, email and image files); and **Meaning on all files** (every file with text, about three times the indexing time of Meaning on documents). The main folder and the libraries Studio builds, on this computer or on a remote system, start at Meaning on documents. On a remote system, the first build sends Studio's embedding model and its packages for the Python there (about 70 MB, once, kept in `~/.activate-studio/embed`); the connection test says whether it can. Libraries added by an earlier version keep the depth they had. Change any of them in Settings, Indexing, Libraries, in the Depth column. Search by meaning is the slowest part of indexing, so it runs last, in the background: a new library is searchable by name once its folders are indexed, then by its words, and the line above the results says when its meaning is still being computed. For a folder of more than about 500,000 files, Text + OCR is faster, and meaning can be added later. For the main folder and a library built on this computer, a change is applied in the background at once, over the files already indexed: only what the new depth adds runs (the text, OCR, or search by meaning), and a lower depth runs nothing. With the background sync paused it waits for **sync now**. A library built on a remote system takes a new depth when it is rebuilt: changing the depth there offers **Rebuild now** or **Later**. The current index keeps answering until the new one replaces it, and the row says **Depth changed, Rebuild to apply** until a rebuild at that depth finishes. On a remote system, Studio also sends its PDF reader, so PDFs are read there with nothing installed. When a build there finishes with files it could not read, the library's row in Settings, Indexing, Libraries says **Ready; some files were not read**, with the count and the reason, such as "312 PDFs have no text: this system has no PDF reader". Fix the reason where one is named and press **Rebuild**: text already read is kept, and only the files without text are read again. A search with quotes or operators, one short word, or a code such as ABC-12 matches words only.

**Searching** above the box picks the libraries: tick any of them, or **All libraries**. Search and Query each keep their own choice in this browser, and each result says which library it is in when more than one is ticked.

**Refine** splits the box in two. **Name or path** takes words, which match any part of a name or a folder, and patterns such as `*.docx` or `reports/*.pdf`, with OR and -word. **Text or meaning** takes the words inside files in full-text syntax (`AND`, `OR`, `NOT`, `"phrase"`, `prefix*`), and the same words without the operators are searched by meaning. By default matches of either kind are listed, each to its own limit, so many name matches never push out the text; with **Search text and meaning only in files whose name or path matches** on, only files that match both are listed, such as the .docx files that mention a budget. The address carries a search, so it can be bookmarked or shared.

When a search leaves a library out, or searches it only in part, a line above the results names it and says why: it is being built, its text has not been read yet, its index is missing, it did not answer within the search time limit, it could not be reached over ssh, or macOS has not allowed Studio to read its folder. Each name opens the library's row in Settings, Indexing, Libraries. Query shows the same line, and the assistant's search says the same in its answer.

Each library's search has a time limit, 20 seconds by default. A library still searching at the limit is stopped, its search ends on its own host too, and it is left out of the results; the line above them then has **Change the search time limit**, which opens Settings, Indexing, Sync and search. There **Search time limit** goes from 10 seconds to an hour, or **No limit**, for very large indexes. While a search runs, **Stop** beside the Search button ends it, and the stop button in the chat ends the assistant's search the same way.

- Use "quotes" for a phrase, OR between alternatives, -word to leave a word out, and word* for words that start the same way.
- Results found more than one way come first, then the best of each kind: a file that uses the words more, in less text; the exact name, then names that start with the search; the passage nearest in meaning. Each library's index is read once per search for all of them.
- Label chips under the box narrow the results.
- Tick results to label them together, or press **Transfer…** to copy or move them to another place (see Transfers). The same path in two libraries is two results.
- **Export CSV** saves the results listed (with **Load more** for up to 1,000) as a CSV file: library, path, name, how each was found, size in bytes, modified time in UTC, labels and the snippet. **Copy** puts the same rows on the clipboard as tab-separated text, which a spreadsheet pastes into columns. In the macOS app the file goes to Downloads.
- **GUFI commands**, under the results, shows the commands that found them, ready to copy and run in a terminal, with where each ran, when, how long it took, and its exit status. **Error output** under a command shows what it wrote to stderr. Lines saying "no such table" for the text or vector tables are expected, from folders without text or vectors, and are counted apart from the rest. On screen a search by meaning's query vector is shortened, as `X'3f2a1b0c…' (384-value query vector)`, and quotes read as SQL without the shell's escapes; a line under the commands says so. **Copy** gives the full command, and the command log keeps it in full.

## Adding material

Drag files or folders onto the tree, or use **Add**, which also takes a web address. New material is searchable in about a second. Files copied in outside Studio are picked up within minutes, or right away with **sync now** at the bottom of the navigation.

# Organize and analyze

## Labels

Labels organize files without moving them. Label a folder and everything in it carries the label, including files added later. Apply labels from the tree, the viewer, search results, or by asking the assistant; filter by them in Search, Query, and the chat's Scope.

With several items selected, the Labels panel lists a label that only some of them carry under **On some of these items**: click it to add it to the rest, or its X to remove it from all of them. The tag button at the top of the tree shows or hides each item's own labels; selecting items turns it on.

In the knowledge base the labels are saved on the files. In any other library, including a read-only folder and an index on another machine, Studio saves them itself, so the files are never changed; the Labels panel says so. They show in the tree, Details, Search and Query like any other, and are removed with the library. The assistant labels files in the library the chat's Scope selects, or in the knowledge base when several are selected and it is among them; otherwise it asks which library.

**Suggest labels** on a folder's right-click menu asks the model to propose labels for the files under it that have none, reusing labels already in use where they fit. It works in any library: in the knowledge base it reads the files and their extracted text, in another library on this computer the files in its folder, and in a library on a remote system the text its index holds, or the file itself over the connection. A library whose files are not on this computer or reachable over a connection, such as an index added without its folder, says so. Accepted proposals are saved like any other label: on the files in the knowledge base, and by Studio in any other library. The assistant's suggestions follow the chat's Scope, as its labelling does.

## Query

Structured questions about the files themselves (largest, oldest, totals by type or owner) answered in milliseconds, in the libraries ticked under **Querying**. Pick a preset under **Start from** and change it, add conditions (all must match, or any), or write read-only SQL, and save the ones you reuse. Sizes take units (`10 MB`), and dates take a day (`2026-01-01`) or a time ago (`7 days`). **GUFI commands** under the form shows what ran, ready to copy, with each command's error output, also when the query fails; the code button beside a saved query, or **Show SQL** for the form on screen, shows the SQL it runs and its command.

The columns of your own SQL are named as SQLite names them: the name after `AS` (`SELECT name AS file, size AS bytes ...` heads the columns **file** and **bytes**), else the column's own name, else the expression as written. A column named `bytes` shows its sizes in units. With `*` in the list the columns are named col1, col2 and so on.

When the rows have a **path** or **directory** column, tick rows to label them or press **Transfer…** to copy or move them (see Transfers). A row totalled over all libraries is no single file or folder, so it can be labeled but not transferred; hovering its box says so.

**Export CSV** above the rows saves them as a CSV file, sizes in bytes, and **Copy** puts them on the clipboard for a spreadsheet. Both take the rows the query returned, up to its limit (2,000 at most); for more, narrow the query or run the command under **GUFI commands** in a terminal.

## Stats

The knowledge base at a glance: size, file types, labels, and recent changes. Click any figure to see the files behind it. While the index is being built the page follows it, phase by phase; **Refresh** reads everything again, and **Index runs** lists recent builds and syncs with how long each phase took.

Each map shows one library, picked beside its title, or in the header at full screen, where the map changes in place, and remembered in this browser: the corpus topology starts on the main folder, the semantic map on the largest library that has one. **Corpus topology** shows the library's folders by size, read from its index, on this computer or on another system, and zooming in shows the folders inside them. The **semantic map** places files by what they say, in clusters, with a sample of up to 3,000 files; click a cluster for all of its files. Each cluster is named for the words that set it apart (or for its folders, where its files have no text), and the folder name shows when you hover it. Both maps zoom (wheel, pinch, + and -), move (drag or the arrow keys) and open full screen, and the semantic map turns in **3D**, where zooming magnifies toward the pointer and turning goes about the middle of the view. **Show links** draws a line from each cluster to the two that read most alike (on by default in 3D), and hovering a file draws lines to its five nearest files by meaning, with a ring where one is not on the map yet. Clicking a file selects it: the map moves to it and zooms in, keeps the lines to its five nearest files, and shows a card with its name, folder and nearest files with their similarity. Clicking a nearest file in the card or on the map selects that file; Escape, the card's close button or a click on an empty part of the map clears the selection. **Open in Library** in the card, a double-click or Enter opens the file in the Library, closing full screen first. Each legend shows its eight largest entries and **+ N more**; hovering an entry shows it on the map, and clicking it opens it. The map is remade in the background after the library's search by meaning changes. A library has a semantic map when it has search by meaning: for one the Studio builds, a depth of **Meaning on documents** or **Meaning on all files**, which the map offers to set. An index connected as it is has one only where it holds the Studio's own vectors. For a library on another system, the Studio fetches the vectors of up to 50,000 of its files over the library's own connection and draws the map here; the map says when it shows a sample, which model the vectors come from and when they were fetched, and **Refresh** fetches them again. It is also checked for changes at most hourly while you look at it, and after a build there. Nearest files are searched for on that system. A library there with no vectors says so; for one the Studio builds there, set its depth to **Meaning on documents** and Rebuild it.

On the ACTIVATE platform, the Workflows tab shows the workflows chosen for Studio. Open a tile, fill in the form, and press **Run**; **Validate** checks the inputs without running anything. Runs use your own account.

- Saved configurations appear as presets at the top of the form.
- Under the title, the form says where the workflow comes from: stored in your account (local), or read from a repository (remote), with its branch and file.
- A form shows the sections and columns its workflow defines.
- A workflow kept in a repository shows its README beside the form, with how it works and what its inputs change. **Hide README** puts it away.
- A workflow from GitHub that asks for access to your account variables waits until you tick the approval.
- Administrators choose the set under Settings, "Workflows".
- Apps that runs open, such as a design explorer or a notebook, are listed under **Sessions**. Click one to show it in a side view on the page, as in chat, or press **Window** or **New tab**. Click a run's id to show its form, graph, and session there; a run started from a form opens there too. When the Studio is open inside ACTIVATE, the session opens on its ACTIVATE page in a new tab. A session started from chat also appears in that conversation.
- Your ACTIVATE desktops are listed there too, and show in the side view, over the whole Studio with **Full screen**, and under their card in a chat, drawn by the Studio. Click in the desktop to type in it. The bar above it has **Fit** (the desktop takes the size of the view; **Scale** keeps its size, **Actual size** shows it pixel for pixel), the picture quality, **Clipboard** (what was copied on the desktop, and text to send to it, which you then paste there as usual), **Ctrl+Alt+Del**, and **Logs**, the desktop's start-up logs. A desktop that is starting shows once it is running; a dropped connection is tried again by itself. ## Agents

Ask the assistant to delegate a piece of work, for example "delegate the Q3 pump test summary to the reviewer", and it hands the work to pw code: one session working in a new library folder under `agents/<instructions>/` (or the folder you name), with the agent instructions you chose written into that folder's `AGENTS.md` and a goal it keeps working toward until it is met. pw code splits the work itself where that helps. The session is on the **Code** page, marked delegated, with a **Delegated** filter; open it to read the conversation and, once it finishes, the files it wrote, which the Studio has indexed. The assistant gives you a link to it and can tell you how it is going.

The Agents tab has three pages:

- **Earlier tasks**: tasks of the earlier task engine, kept to read: their agents, board and output, with a link to their results under `tasks/`. Work you delegate now is on the Code page.
- **Fleet**: standing agents that wake on a schedule or when something changes, and ask you when they need a decision. Each is a pw code session on this computer working in its own folder, `agents/fleet/<name>`, whose `AGENTS.md` holds its instructions and goal; its detail shows the session's latest conversation and links it on the Code page. Agents made before this change are moved over the first time the Studio reads them, and each says what did not carry over.
- **Instructions and skills**: how agents should work, written once and applied to the folders they work in. **Apply to a folder** writes instructions into that folder's `AGENTS.md`, which pw code reads in every session there, beside your own text in the file, and a skill into the folder's `.agents/skills`. The list of folders under them shows where each is applied, with **take off** to remove it. pw code uses a folder's skills once you have opened that folder in pw code and approved it; its `AGENTS.md` applies at once.

Delegation is turned on under Settings, "External access".

You can also ask the assistant to run a pw code agent on one of your clusters, for example "start an agent on my cluster in ~/project to fix the failing tests, and keep going until they pass". It starts a pw code session there with your key and gives it the goal, so the agent keeps working until the goal is met or a turn limit is reached. Ask the assistant how the agent is doing, give it direction, or pause, resume, or clear its goal. You can open the same session in a terminal with `pw code attach <cluster>/<session>`.

pw code is a full coding agent, so it suits work the assistant's own tools do not cover, such as a report built with code and figures: "have pw code write the site survey report as a PDF in reports/survey". When the agent runs where your library is (this computer, or a cluster with the library on the same machine or shared storage), it works in a library folder: the one you name, or a new one under agents/. When it finishes, the assistant indexes that folder and links what the agent wrote, and the files open in the Library. The assistant can wait for the agent to finish and tells you if it stopped on an error.

To pick up a session you already have, name it or say what it was about, for example "check on my pw code session about the budget workbook". The assistant finds it among your sessions by its name, the topic pw code gave it, and its first request, and asks which one if several match. On a computer of its own, with sign-in off, this works without an ACTIVATE account, using pw code on this computer.

## Code

Where ACTIVATE is not available to you (no ACTIVATE key on a Studio with sign-in off), Code lists this computer's own pw code sessions instead, read from its pw code, to read and follow; there is nothing to open in ACTIVATE, and continuing one in a Studio chat needs ACTIVATE as before. On ACTIVATE, Code lists your pw code sessions on the platform's machines, the same ones the platform's Code page shows: those waiting for you first, then those working, then the rest, with archived sessions behind **Show archived**. The line under the filter names the machines whose pw code daemon is running. Choose a session to read its conversation; it updates while the session works. Tool calls in a row fold into one line, such as "6 tool calls: ReadFile 3, EditFile 2, Bash"; click it to see each call by what it worked on (the file, the command's first line, the search, or the to-do item under way), and click a call to see its result. **Open in ACTIVATE** opens the session on the platform, where you answer, approve and steer it, and **New session in ACTIVATE** starts one there.

**Continue in Studio** carries a session on in a chat here, when it is on the machine where this Studio's pw code runs for you: this computer, or, on a Studio several people share, your own pw code on the Studio's cluster. It asks first, since the session may also be open in a terminal or in PW Code on the web, and messages from there reach it too; a session open on another machine is taken over from there. The chat starts with the session's earlier turns, and each message, approval and stop goes to that same session, which pw code answers. Sessions on other machines and archived ones stay read only, and the line under the button says why. A session that is in a Studio chat says so in the list, and **Open the Studio chat** opens it. In that chat, the first message and the **pw code** menu link back to the session here. A session started outside the Studio keeps its own tools: pw code cannot add the Studio's library tools to a session that already exists.

## Getting around

The address bar follows what you are looking at, so back and forward work and a copied link opens the same place for someone else.

- **Search**, at the top of the navigation, searches the knowledge base; Ctrl+K (⌘K on a Mac) jumps to it from anywhere.
- In the desktop app, Ctrl+= and Ctrl+- (⌘= and ⌘- on a Mac, also in the View menu) make everything larger or smaller, and Ctrl+0 (⌘0) returns to actual size. The app opens at the size it was left at. In a browser, the browser's own zoom does this.
- The navigation groups its pages under **Knowledge** and **Run**; click a group's name to fold it away, and Studio remembers.
- **Install app**, in the navigation, installs Studio as a desktop app in its own window. If a classification banner is shown, the chevron in Chrome's title bar moves the banner into the title bar. The loading screen draws the banner as it was last shown, so the title bar has no gap while the app starts. The window opens in the color of the theme you last used, light or dark, before the page appears. After the first visit, the browser keeps the app's own files on your computer, so the Studio starts within a fraction of a second even when the network is slow; when a new version has been deployed since, the line at the bottom of the navigation says **Updated to** with **Reload**.
- The bottom of the navigation shows who you are signed in as, whether the models are reachable, and the state of the index; click any of them for details.
- A status reads the same everywhere: a blue pulsing lamp is work under way, green is done or ready, red is a failure, amber needs a look or an answer, and an unlit ring is idle.
- **About**, at the foot of Help's list and in the version's panel at the bottom of the navigation, shows the version and license. ACTIVATE Studio is built and maintained by Parallel Works.
- The **status panel** at the right shows what is running (delegated pw code sessions, standing agents, workflow runs, open sessions), your libraries and the last index sync, the model in use (while AI features are on), and **Connections**, when there are any: the ACTIVATE platform, attached MCP servers, and the machines that hold remote libraries, each with its state. The panel button at the top right of each page opens and closes it, and Studio remembers. Click a card's header for its detail; click a run or session to open it beside the chat or on the Workflows page. While a run or session is open beside the chat, the panel steps aside. Phones do not show it.

## Setup and the sidebar

On a computer of its own, with nobody signing in, Studio opens with a short setup, one step at a time. **Skip this step** moves past a step without changing it, and **Finish later** closes setup at any step; everything in it is also in Settings.

- **Your Studio**: the name, an icon for light mode and an optional one for dark mode (PNG, JPEG, SVG or WebP, up to 1 MB; the browser tab uses it too).
- **Appearance**: Light, Dark or System (which follows the computer's own setting), and the accent color. The default accent, None, has no color: buttons and highlights are near black on light and near white on dark. Both apply as you pick them.
- **AI features**: optional, and off on a new install until turned on here. On, with the OpenAI-compatible endpoint (a site AI portal, a provider, or a model server), its key (empty for a model server that takes none) and the default model; **Test** lists the models the endpoint offers or says what failed, and whether the model calls tools. An ACTIVATE account works too, set up in Settings, Model access, as is a portal that needs the Advanced options there. Off, Chat and Agents leave the sidebar and the guide, the footer and status panel drop their model lines, and nothing is sent to a model. Settings hides what only the assistant uses: Assistant tools, Feature previews and Extensions, the mission, suggested questions and captioning model on the AI features tab, image descriptions under Indexing, Building, and the grounded model, delegation and attached MCP servers under External access. Model access becomes **ACTIVATE access**, with only the ACTIVATE credential the Workflows page and ACTIVATE libraries use. Label suggestions in the Library and chat activity on the Stats page go too. Search, search by meaning, the library, query, statistics and the MCP endpoint work as before. AI features can be turned back on at any time in Settings, General, AI features, and everything returns at once.
- **Sidebar**: which pages it shows; Workflows starts hidden on a new install. Workflows runs ACTIVATE workflows and needs an ACTIVATE credential; for workflow YAML files of your own, without ACTIVATE, use [Meridian](https://github.com/parallelworks/meridian), the open-source workflow engine.

On a new install the AI features page starts with a mission written for one person's own files and ten suggested questions; the empty chat shows four of them at a time. A blank mission, or questions left as they came, keep following the defaults.
- **Your folder**: the folder to index. In the macOS app and the Linux app's window, **Choose another folder…** opens the system folder chooser; elsewhere the folders show in the page. Choosing another folder restarts Studio on it in the macOS app, then offers to build its index; elsewhere, set `KB_ROOT` and restart. **Index depth** sets how far its index goes, from names only to meaning on all files (see Search). **Build the index** runs in the background: go on with setup, or finish it, while it runs, and the steps after show how far it has got. Indexes can be added or changed at any time in Settings, Indexing, Libraries.
- **Other libraries**: GUFI indexes that already exist, on this computer (typed or picked from its folders), on another machine over ssh, or, when the pw CLI here is signed in, on one of your running clusters through ACTIVATE. A machine whose login runs only `gufi_query` (no bash, or a restricted shell) works too: give the index directory as an absolute path and leave the GUFI bin directory empty; you can browse, search and query it, but not open its files or build an index there. A machine behind a jump host works too: give its Host alias from `~/.ssh/config` (with ProxyJump there), or put `-J you@jumphost` in **SSH options**, which also takes a port, an identity file and `-o` settings such as `ConnectTimeout=20`. The connection test says which jump host it went through. Studio keeps the ssh connection to each host open for ten minutes after it is last used, and opens it as Search or Query opens, so searches and queries a few minutes apart do not log in again. Libraries that reach the same account on the same host with the same SSH options share that connection and are searched in one pass, whether the host was given as `you@host` or as an alias; a library with SSH options of its own gets its own connection, so they always apply. Settings, Indexing, Libraries shows each one as the `user@host` ssh reaches. An index whose text and vectors GUFI's extraction wrote as external databases in GUFI's common schema is searched by that text, and the chat reads its files' text, with no indexing by Studio; its vectors are searched by meaning when they were made with the model Studio uses. The connection test says whether a connected index has vectors, which search by meaning needs; **Check** on the row of a library connected with an earlier version records it. **Import a library list from your administrator** adds the libraries in a library list file instead (see Settings, Indexing, Libraries). The Library's Add menu imports one too.

**Run setup again**, in Settings, General, and **Run Setup…** in the macOS app's menu open the setup later. Each step shows what is set now and changes nothing until you change it; leaving partway keeps what was already saved.

Settings, General has a tab for each part: **Appearance** (theme, accent, surface tone; the default surface is Warm gray, a gray with a slight warmth, and Neutral gray has no tint; then, under Branding, the name, icon and classification banner), **Sidebar** (the pages it shows and its width), **AI features** (the switch, the mission and context the assistant works from, the suggested questions under an empty chat, and image captioning), **Updates**, and **Server** (the port). Settings, Model access has the model endpoint.

Settings, Indexing has a tab for each part of indexing: **Libraries** (the main folder and every other library, their depth, and Add a library), **Sync and search** (search across libraries, the search time limit, the background sync interval, history snapshots), **Building** (threads, the main folder's depth, how files are read, the speed of search by meaning, and what this computer can read), and **Storage and logs** (where the index is kept, and the GUFI command log). Sync and search and the GUFI command log have Save settings; everything else on these tabs saves as it changes.

Settings, General, **Sidebar** has a switch for each page. A page switched off leaves the navigation, and a link to it opens the first page still shown. Settings and Help always show, and the switches apply to everyone using this Studio. **Width** sets how wide the sidebar is when it is not collapsed: Narrow, Default or Wide. Its right edge can also be dragged, from Narrow up to 400 pixels, and a double click there returns it to Default; after a click or a drag on the edge, or with it focused from the keyboard, the arrow keys move it (Shift for larger steps). The width applies at once and, like the switches, for everyone using this Studio.

On a computer of its own, the suggested questions and the mission start out written for one person's own files; change them under Settings, General, AI features.

## Signing in

A shared Studio may ask you to sign in. Choose **Sign in** at the bottom of the navigation, sign in with your organization's account, and you come back to the page you were on. Your name then shows in its place; a click on it shows what the sign-in says about you and has **Sign out**. **Sign out** ends your session in Studio; your organization's sign-in stays, so signing in again may not ask for your password. If Studio is open inside the ACTIVATE platform's session view, **Sign in** opens a new tab, since sign-in does not complete inside that view; keep using Studio in that tab.

Signing in tells Studio who you are. It does not let Studio act for you on the platform: running workflows or using the platform's models as yourself still needs your own key under Model access.

## Model access

Settings, **Model access** shows where Studio gets its models, with the models available or what failed; **Re-check** asks again. **What each part uses** lists the credential behind models, the Workflows page and the assistant's platform tools, libraries on ACTIVATE systems, and ChatGPT and Copilot subscriptions. All but models also run the pw CLI. When Studio cannot find the CLI, the ACTIVATE (pw CLI) tab says so and takes its location (`command -v pw` in Terminal prints it).

- **ACTIVATE (pw CLI)**: the ACTIVATE platforms the pw CLI on this computer is signed in to, one row per context. **Use** picks one; with **Follow the pw CLI's current context** ticked, Studio uses whichever `pw context use` last chose. **Sign in** signs the CLI in to another platform: it shows a code, you approve it in a browser on any device, and Studio uses the new sign-in.
- **ACTIVATE API key**: a token or API key from an ACTIVATE account, which covers models and the platform. The host is the platform's own, such as `platform.example.com`. An address with a path, such as `https://portal.example.org/v1`, is an API rather than a platform host: the tab says so, and **Use as an endpoint** moves it and the key to the next tab.
- **OpenAI-compatible endpoint**: any service that speaks the OpenAI API, such as a site's AI portal, Ollama, LM Studio or vLLM on this computer, the OpenAI API, or GitHub Models with a token that has the Models permission. The base URL usually ends in `/v1`. **Advanced** is for portals that differ: the header the key goes in (`Authorization: Bearer` unless set to `api-key`, `x-api-key` or none), extra headers, model names for an endpoint that does not list its models, and a query string such as `api-version=...`. Header values are stored like the key and never shown again. An endpoint covers models only; platform tools keep using the pw CLI.
- **Subscriptions through ACTIVATE** connects a ChatGPT plan, with a code you enter at OpenAI, or GitHub Copilot, once your GitHub account is linked in ACTIVATE. The platform keeps the connection, and its models appear with the others. The list is checked again when you sign in, sign out or change the key.

**Test** checks that the endpoint answers, then sends the model one small request with a tool. Chat searches your libraries through tool calls, so a model that answers without calling the tool cannot search them; Test says so, and you can pick another model or turn tool calling on where the model is served. Saving works either way.

On a shared deployment, **Where access comes from** lists your choices, with **Sign in with ACTIVATE** first and recommended. It shows a code to approve on the platform, then the Studio keeps the sign-in for you alone and renews it until you choose **Sign out**. While you are signed in, it is your credential for models, the Workflows page and My library, before an **ACTIVATE API key** you added; an **OpenAI-compatible endpoint** you chose still serves models. Without any of these, requests use the deployment's credential (**ACTIVATE (deployment)**). If a sign-in does not finish, the page says what the pw CLI reported, and the server log has its full output and version.

## Working offline

With no network, Studio keeps working from its libraries: browsing, search, query, statistics and adding material. Chat keeps working with a model server on this computer, set under Model access, OpenAI-compatible endpoint. Anything that needs the network says so in one line instead of waiting: the model banner and the footer show **offline**, the Workflows page says the platform cannot be reached, and the update check shows **Offline** and tries again later.

## Networks that inspect HTTPS, and proxies

Studio trusts the certificate authorities this computer trusts as well as its own list, so a network that inspects HTTPS works once its authority is installed on the computer; on a Mac, in Keychain Access or by the Mac's management. Behind a proxy it uses `HTTPS_PROXY` and `NO_PROXY`, and the macOS app takes the proxy from System Settings when none is set, except one given by an automatic configuration (PAC) file. A certificate or proxy problem is said in one line, for example on Settings, Updates, instead of being shown as offline.

## Using it from other tools

Other tools can use this knowledge base. pw code and other MCP clients can search it directly, and any OpenAI-compatible client can use it as a model that answers from it. Settings, "External access" has the addresses and the exact commands.

## Updates

When a newer version is available, the version at the bottom of the navigation says **update available**, tinted blue, and the collapsed navigation shows a blue dot in its place. A click on it opens the **Build** panel, where **What's new** lists the changes in each newer version, and a click on one reads it. In the macOS app, and in the Linux app installed in your home folder, **Update now** downloads the release, checks its signature, installs it and restarts, and the page reloads on the new version. While it installs, the same line says **updating…** and the Build panel shows the progress; if the install fails, the line says **update failed** and the panel says why. A Linux copy installed from a .deb or .rpm package does not update itself: **What's new** shows the `apt` or `dnf` command that does, and the Studio is then quit and reopened. A copy run from a clone of the repository shows the commands that update it in the Build panel and under **What's new**. With nothing newer known, the same line offers **check for updates**, and the Build panel shows when the last check ran and **Check now**. In the macOS app, **ACTIVATE Studio, Check for Updates…** in the menu bar opens Settings, Updates and checks.

Settings, General, **Updates** has the same, and **Roll back**, which downloads the version installed before again and installs it, so it needs this computer to be online; it saves the settings and conversations as they are first, so what was made on the newer version is kept in a snapshot. **Roll back** is not offered after the update from v1.188 or earlier, which ran the Node server; if the new version fails to start three times in its first minutes, the app puts the earlier version back by itself. The app checks a minute after it starts, then every 15 minutes, and when its window opens after a longer gap (time the Mac was asleep counts), unless **Check for updates automatically** is off; with **Install updates automatically when idle** on, it installs a new version once no chat reply or indexing has run for ten minutes. The first time Studio opens on a new version, **what's new** appears beside the version at the bottom of the navigation and opens the list of changes. When an update also changed the macOS app's own window (the title bar, the Dock icon), the app reopens on its own after an update you started; after one installed while idle, a line above the version says **Reopen to finish updating** with **Reopen now**, Settings, Updates offers the same button, and the line stays until the app reopens. A hosted deployment is updated by its operator and shows none of these, except a deployment of a GitHub release through the ACTIVATE workflow: the person who launched it gets Settings, Updates and the same lines at the bottom of the navigation, and the page reloads onto the new version once it is installed.

**Channel** is Stable or Preview; Preview gets new versions first. **Install a version** installs any release on the channel since v1.188.1, older ones included, and on Stable while running a Preview, **Move to Stable** installs the newest Stable (v1.189 or later). Studio saves your settings, conversations and credentials before every change of version, and puts the saved copy back when an older version cannot read them.

To remove the macOS app, choose **Uninstall ACTIVATE Studio…** in its app menu. It lists everything it removes, with your indexes, settings and logs included unless you untick them, and never removes your documents.

**What's new**, at the top of Help, lists every version's changes, newest first. The version at the bottom of the navigation and Settings, Updates open it too.

## The index

Studio is built on GUFI, the Grand Unified File Index from Los Alamos National Laboratory: a tree of small databases, one per folder, holding each file's details, its text, and search vectors. Access follows the file system's permissions, and a change re-indexes only the folder it touched.

A build runs in four phases, each with its own count: **names** (every file and folder, searchable by name as soon as this phase ends), **documents** (PDFs and Office files converted to text), **text** (images, other formats, and the full-text tables), and **meaning** (embeddings for search by meaning, at the two meaning stops). At the Names depth only the first phase runs. The index line at the bottom of the navigation, Settings, Indexing, Libraries, and Stats all show the same progress. Click the index line for the phases, **Stop**, and **View log**, the index log as plain text. Text and embeddings are kept between builds, so updating an index, or choosing a folder that was indexed before, redoes only what changed. A build that a shutdown or a quit cuts off is taken up again at the next start, and everything it had read is reused.

Studio uses GUFI 0.8.1. An index built by an earlier GUFI keeps working: nothing needs to be rebuilt, and the update does not touch it. The one exception is an index written by GUFI 0.7.0 or earlier that has rolled-up folders, which 0.8.0 lists more than once; search and Query then name that library as searched in part, and Settings, Indexing, Libraries says to rebuild it. A query of your own that names the `dev` column needs an index built with 0.8.0, which a rebuild gives it.

On macOS, a folder in Desktop, Documents or Downloads, in iCloud Drive, or on a removable or network volume can be read only once macOS allows it, in System Settings, Privacy & Security, Files and Folders (or Full Disk Access). Until then Studio indexes the rest, names the folders it could not read in search and Query, and keeps what it had indexed of them.

Settings, Indexing, **Storage and logs** has **Log GUFI commands**, which writes every command Studio runs to read an index to a log file, named there: when it ran, for what (search, query, the assistant, statistics), how long it took, how it ended, and the end of its error output. The same tab says where the index is kept and can move it. Settings, Indexing, **Building** sets how many threads each phase uses (one per processor core by default), the main folder's index depth, how documents are read (the PDF reader for files the converter cannot read, LibreOffice for previews and for Office files the built-in readers cannot read, and, from Text + OCR up, image descriptions by the vision model chosen under AI features), the speed of search by meaning (**Standard**, or **Faster**: the first 128 tokens of each passage rather than 256, in well under half the time, with slightly lower ranking). Libraries built of a folder on this computer follow the same threads and readers, and each has its own depth, in Settings, Indexing, Libraries. It also lists which file types this computer can read and which index by name only: older Office files (`.ppt`, `.xls`), OpenDocument, Apple Mail messages (`.emlx`) and `.eml` files are read with nothing to install, and for each tool still missing (OCR, poppler, LibreOffice) it says what the tool adds and gives the command that installs it here, with **Check again** and **Update the index now** once it is found.

A format Studio does not read can be given a reader of your own: a program that takes a file's path and prints its text. List it in `extractors.json` in the index folder (where the index is kept, Settings, Indexing, Storage and logs), or in the file the `STUDIO_EXTRACTORS` environment variable names, as `{"extractors": [{"name": "dwg", "suffixes": [".dwg"], "command": ["/usr/local/bin/dwg2text", "{path}"], "timeoutSeconds": 120}]}`. `{path}` is replaced by the file's path, or the path is added at the end; no shell is used. The program is stopped after `timeoutSeconds` (120 when left out, at most 3600). It can also take over a format Studio reads, but not plain text formats. The file is read by the document extraction pass of the Go server; a broken `extractors.json` in the index folder is logged and skipped, and one named by `STUDIO_EXTRACTORS` stops the pass with an error. CUSTOMIZATION.md has the full contract.
