# Delegated agents

## Delegation to pw code

When delegation is on (Settings, External access, Delegation), the chat's `delegate` tool hands a piece of work to pw code: one session, started by the same path as `start_agent`, in a library folder with the chosen agent instructions in that folder's `AGENTS.md` and the goal set. pw code does its own splitting, so there is no subtask tree, no board, and no result contract; what the agent writes in its folder is the result.

*Folder.* The one the model names (relative to the main library's top), or a new one, `agents/<instructions>/<date>-<time>-<first words of the objective>` (`agents/delegated/...` with no instructions). The instructions are written before the session is made, so its first turn reads them, through the same writer and rights as Apply to a folder: the main library only when it can be written here. Where it cannot, or the site does not see the library, the session works in a folder of its own on the site (`~/studio-agents/...`), the instructions open its brief instead, and its files are not indexed; a folder the model named is refused instead.

*What runs without asking.* Delegated sessions and standing agents run in pw code's accept-edits mode: they read and edit in their folder without asking, and every shell command, and any read outside the folder, waits for a person. pw code's allow rules match a command's text, so they cannot say "a command that only reads, inside this folder" (`Bash(ls *)` also matches `ls > file`). On this host's daemon the Studio therefore creates the session with `allowedTools` it can state exactly (`agentsmd.ReadRules`): `ReadFile`, `GlobSearch` and `GrepSearch` anywhere under the main library's top (pw code checks these path rules against the resolved path, so a library reached through a link is named both ways), and a few whole commands that only list or print the folder: `pwd`, `date`, `ls`, `ls -l`, `ls -a`, `ls -la`, `ls -al`, `ls -lah`, `ls -alh`, `ls -R`, `ls -lR` and `tree`. pw code checks every stage of a command, so `pwd; ls -la` runs while `ls -la notes`, `cat file` or `ls > x` asks. The daemon refuses `allowedTools` from a remote origin, so a session on a cluster gets none. The first message of a delegated session, and a standing agent's `AGENTS.md` section, carry a note (`agentsmd.WorkingNote`) telling the agent to read, list and search with its file tools and to append to a file by editing it, so it rarely needs the shell. A standing agent's session made before this keeps its earlier rules until it is renewed (after six days, or when its folder changes). What still waits is answered on the Code page.

*Goal.* The model's completion condition, or by default that the work in the brief is done with its outputs in the folder, bounded by `max_turns` (default 20). Strands the model passes as `subtasks` are listed in the brief as a suggestion.

*Record and finish.* The Studio records each delegated session per person (`INDEX_BASE/delegation/sessions.json`, mode 600, the last 500): site, session, folder, instructions, objective, goal and state (working, waiting for approval, finished, stopped on an error, or gone). It watches the session every 20 seconds for up to 12 hours; when the session settles it indexes the folder and records its 50 newest files. `agent_status` on the session does the same when it finds it settled. After a restart the process that holds the index lock watches local sessions still working again; a session on a cluster needs the person's key, which is not kept, so it is brought up to date when the person or the assistant next looks at it. `GET /api/delegated` answers `{sessions}`, the person's records, newest first.

*Where it shows.* On the Code page: delegated sessions are marked (with their instructions), a **Delegated** filter shows only them, and a delegated session's detail says which folder and instructions it has and links the files it wrote once it finishes. A call the session waits to have approved shows there with **Approve** and **Deny** (`POST /api/code-sessions/approve`, one call at a time, no standing grant), for delegated and standing agents' sessions as for any other, where the Code page lists this computer's sessions (sign-in off, or `AGENT_LOCAL_SITE=1`). A standing agent's session is on this computer, so its detail on the Fleet page shows the call it waits on, whole, with **Approve** and **Deny** (`POST /api/fleet/<id>/approve` with `approval` and `allowed`, its owner and the administrators only, one call, no standing grant), on any Studio. The delegate tool's answer links `#view=code?session=<id>`. The Agents tab's Earlier tasks page is not a second view of these: the Code page already lists the sessions with their transcripts, so that page keeps only the tasks of the retired engine, to read.

*Code page without the platform.* When the platform is not available to the viewer (the same test as the Workflows tab: no credential for it) and the Studio offers its own host as an agent site (sign-in off, or `AGENT_LOCAL_SITE=1`), `/api/code-sessions` reads this host's pw code daemon over its socket (`/v1/status`, `/v1/sessions`, `/v1/sessions/<id>`), in the shapes the platform passes on, as one machine named "This computer". `/api/config` then has `localCode: true`, and the Code tab shows. With sign-in on, the Code page reads the platform only with the person's own ACTIVATE credential (their sign-in, or a key of their own), never the deployment's, and answers 409 without one: the Studio's account runs other people's delegated and standing agents. It reads this host instead only for a signed-in person with no credential of their own, and then lists, opens and answers only the sessions the Studio started for them (`app.Providers.OwnSessions`: their pw code chats, delegations and standing agents); any other session there answers 404.

## Standing agents (fleet)

A standing agent on the Fleet page is a long-lived pw code session on this Studio's host, working in a library folder of its own, `agents/fleet/<id>/` (in `INDEX_BASE/fleet/<id>/work` when the main library cannot be written here). Its `AGENTS.md` holds its agent instructions (the persona chosen for it) and a `standing_agent` section with its name, its goal, the system it works on if one is named, and how to answer a wake-up. Both are written when the agent is made, so the folder and its `AGENTS.md` are there before the first wake-up, and again before every wake-up, so an edited goal or instruction reaches the session. Its record (`INDEX_BASE/fleet/<id>/agent.json`) and journal (`journal.jsonl`) are the Studio account's alone, files 0600 in folders 0700, as the delegation records are; records written open by an earlier version are closed when the Studio reads them.

*Who sees an agent.* On a Studio with sign-in, an agent is the person's who made it, and the Studio's administrators': every `/api/fleet` route answers only them, and another person's agent is answered as no agent at all (404). An agent kept without an owner is its administrators' alone. The answers leave out the record of the person an agent acts for (`ownerUser`, with their groups and sign-in claims), which stays on the server for its wake-ups. On a Studio without sign-in, its one person sees every agent.

*Wake-ups.* An agent wakes on its schedule (15 minutes to a day, or manual), when a platform run ends (where this process owns the platform's jobs), when files change under a watched library folder, when a person writes to it, or with **Wake now**. A wake-up is a message to its session saying what woke it, with the person's messages, and a goal for that round: the round's work is done and its status reported, within the agent's turns per wake-up (default 10). The session carries the Studio's tools through the same MCP server and token a pw code chat gets, acting for the person who made the agent; the token lasts 7 days, so a session older than 6 days is archived at the next wake-up and a new one started, which is told the agent's latest results. When the Studio's tools cannot be attached the session starts without them and the journal says so. A session that is gone (archived elsewhere, or the daemon lost it) is replaced the same way.

*Journal and decisions.* The session's history is the agent's working record, shown in its detail and on the Code page. The Studio keeps a short event log beside the record (`INDEX_BASE/fleet/<id>/journal.jsonl`): created, each wake-up and why, each round's final answer, messages, errors and state changes. A round that ends with a line starting `NEEDS DECISION:` puts the agent under **Needs you** with that question; so does a session waiting for an approval. A message while the agent works is given to the running turn; otherwise it wakes the agent now in the same session.

*Budget.* Maximum wake-ups and maximum tokens pause the agent when reached; tokens are the input and output tokens of its pw code sessions. Pause stops wake-ups and lets a round under way finish; Retire, after the page asks, stops the agent and archives its session, which stays readable on the Code page.

*Page.* `GET /api/fleet` and `GET /api/fleet/<id>` look at the sessions of working agents (or the one asked for) before answering, within 5 seconds, so a round that ended shows without waiting for the scheduler's next pass. An idle agent's note says it waits for its next wake-up; the page shows the time from `nextTickAt` in the reader's own time, and journal times likewise. A round's result is shown as markdown. The page tells the Status panel when it changed an agent (the `ade:fleet-changed` window event), which then reads the fleet at once.

*Agents made before this change.* A record from the task engine (where a tick was one delegated task) is taken over in place the first time the Studio reads it. Goal, persona, triggers, budget, counts and journal carry over; the record and its journal say what did not:

- a campaign agent's ticks were platform workflow runs on a named system; it now runs on this host, with that system named in its `AGENTS.md` so it can still submit runs there;
- a model that is not a pw code model id (a Studio model) falls back to pw code's default model;
- tokens counted before were the Studio model's; pw code session tokens add to them from then on;
- a tick that was running is not resumed; its result, if any, stays under `tasks/`;
- the task board's tools (posting to the board, spawning helpers) are gone; pw code splits its own work.

`/api/fleet` keeps its routes and record shape: `GET /api/fleet/{id}` adds `session` (`id`, `earlier` sessions, and `recent`, the last 40 lines of its history), and a record has `engine: "pwcode"`, `folder`, `session`, `sessions` and `migrated`.

## Earlier tasks (the retired task engine)

Before delegation moved to pw code sessions, the assistant split a request into subtasks and gave each to an agent of the Studio's own task engine: one-shot `pw code -p` runs, sessions of this host's daemon, or, for a campaign, platform workflow runs, which shared a task board and answered through a JSON result contract. That engine is gone, with its board, runner, campaign runs, routes and the "Agent execution" setting (`AGENT_EXECUTION` is no longer read).

What it left stays readable. Each task's last snapshot is `INDEX_BASE/tasks/<id>/state.json`, its board `board.jsonl` and each agent's output `work/<agent>/live.log`; its results are files in the library under `tasks/<id>/`. The **Earlier tasks** page on the Agents tab lists those tasks, newest first, each card counting its agents by how they ended (done, failed, stopped: `GET /api/tasks` answers `done`, `failed` and `stopped`, so a task whose agent failed does not read as done), and shows a task's agents, board and each agent's output, with a link to its results in the library; nothing there runs, approves, steers or cancels. A task or agent that was still working when the engine was retired shows as canceled, with "stopped when the task engine was retired". An agent that worked as a pw code session names it and links the Code page, where it may still be listed. `task_status` in a chat reads the same records. The routes are read-only: `GET /api/tasks`, `GET /api/tasks/<id>` (with its board; `since` for messages after a sequence number) and `GET /api/tasks/<id>/agents/<name>/output` (the last 16 KB).

## Agent instructions in AGENTS.md

pw code reads `AGENTS.md` from the folder a session works in, and outside a git repository from that folder only. The Studio writes agent instructions there: applying an instructions template (a persona file) to a library folder puts its text into that folder's `AGENTS.md`, inside a section between two markers that name the template:

```
<!-- ACTIVATE Studio instructions reviewer: begin. ACTIVATE Studio replaces this section ... -->

(the template's text)

<!-- ACTIVATE Studio instructions reviewer: end -->
```

The file is made when there is none. Applying the same template again replaces its section where it is, and taking it off removes the section, and the file when nothing else is left in it. A second template gets a section of its own. Text outside the markers is the person's and is never changed; a section whose end marker was removed by hand is reported and left for the person to mend. The Studio never writes through a link: an `AGENTS.md` that is a symbolic link (to a shared `CLAUDE.md`, say) is refused.

The folder is in the main library, written as the Library writes there and indexed like any file, or in the person's own library (My library), read and written as them over their own session and indexed as that library is. A folder shared with the person, and any other library, is refused.

*Skills.* pw code finds a workspace's skills under `.agents/skills/<name>/SKILL.md` there, and the person's own under `~/.agents/skills`. Applying a skill to a folder writes its `SKILL.md` there, with the front matter pw code reads (`name`, `description`) and a line saying the Studio wrote it; the Studio replaces or deletes only a file that carries that line. pw code loads a workspace's skills only once the person has approved that workspace, which pw code asks at the first interactive launch there (`pw code` in the folder, or `pw code -r <session id>`); a session the Studio starts through the daemon reports the workspace as not yet approved and does not see them, while `AGENTS.md` applies at once. Until a skill is trusted with `/skills trust <name>`, its instructions load but its `allowed-tools` and shell lines stay off. The Studio's own chat assistant keeps loading skills mid-conversation as before.

*On the Agents page.* Instructions and skills, on the Agents tab, applies a template or a skill to a folder (main library or My library; the folder defaults to `agents/<name>`) and lists the folders that carry them. The main library is found by a walk for `AGENTS.md` files and `.agents/skills` folders (to ten levels and 20,000 folders, hidden and machinery folders skipped, links not followed, reused for 20 seconds), each read for its markers, so a file with no Studio section is not listed. My library is on a cluster and read as the person, so it is not walked: the Studio keeps a record of the folders it wrote in there, per person (`INDEX_BASE/agents-md/space-folders.json`), and reads each again when it lists them.

*In a chat.* The Studio assistant takes a persona chosen in a chat as its stance in the system prompt, as before. A pw code chat with a persona works in `agents/<persona>/`, in the main library on a Studio one person uses and in the person's own library on a shared one, with the persona written into that folder's `AGENTS.md` before the session is made. Choosing another persona, or none, starts a session in that folder and archives the old one; a session continued from the Code page keeps its own folder. Where neither library is one the session sees, it works where it would without a persona.

*Routes.* `GET /api/agents-md?library=&folder=` answers the folder (`library`, `label`, `folder`, `path`, `space`) and what the Studio has put there: `exists`, `instructions` (the sections, in order), `skills`, and `problem` when a section cannot be read. `POST /api/agents-md/apply` and `POST /api/agents-md/remove` take `{library, folder, instructions, skills}` (a template name, and a list of skill names) and answer the same. `GET /api/agents-md/folders` answers `{folders}`, each a folder as above. `library` is empty for the main library and `folder` empty for its top; a folder is relative to the library's top, with no `..` and no hidden or machinery folders.

## The pw code daemon

The Studio talks to this host's pw code daemon over its Unix socket (`$XDG_STATE_HOME/pw/code-<hostname>.sock`, or `PW_CODE_SOCKET`), which only the account that runs the Studio can open. When no daemon is running, the first session the Studio starts there starts one with the Studio's own platform context (`PW_CONTEXT`), since a daemon started without a context binds to whichever context is current for that account. The daemon must speak protocol 2. Delegated work at the local site, standing agents and pw code chats all use it.

## pw code agents at sites

The assistant can run pw code agents directly, on one of the user's clusters or, where offered, on the Studio's host. These are pw code sessions the user could also start in a terminal; the assistant's tools start, follow, and steer them (`agent_sites`, `agent_sessions`, `start_agent`, `agent_status`, `agent_steer`, `agent_goal`, `agent_approve`, `agent_stop`).

*Transport.* A cluster's daemon is reached the way `pw code attach` reaches it: the Studio server runs `pw ssh <cluster> pw code daemon proxy --ensure`, which bridges the ssh session to that machine's daemon socket and starts the daemon if none runs, and speaks the daemon's HTTP API over the pipe (`server/src/pwcodeBridge.ts`). One keep-alive bridge per user and cluster carries every request; the first pays for the ssh setup (about 5 seconds), later ones take about a quarter of a second. The bridge closes after 10 idle minutes. This needs only `pw ssh` and a pw CLI with `pw code daemon proxy` on the cluster (v7.120 or later), not the platform's agent routes.

*Credentials.* A user's agents act with the key their chat uses (Settings, Model access), so each connection is that user's and the session runs as them on the cluster, with their files and their pw login there for models. The deployment's key stands in only when sign-in is off and the Studio has one user. Through the bridge the Studio has the owner's authority over that daemon, so it sets each session's permission mode: accept-edits by default (edits in the workspace, asks before commands), or read-only or plan.

*Goals.* `start_agent` creates the session in a workspace (a new directory under `~/studio-agents` unless one is named), sends the objective, and, when a goal is given, sets it through the daemon's `/goal` route. The goal is checked after every turn by an evaluator; while it is not met the session starts another turn on its own. pw code puts no limit on a goal, so the Studio writes one into the condition ("if this is not met within N turns, stop and say what remains", 20 by default). `agent_status` reports the goal's state and the last check (turns, met or not and why), approvals waiting, and the end of the transcript. Approvals are answered only on the user's decision in the conversation.

*Local site.* The Studio's host is a site only when sign-in is off, or when `AGENT_LOCAL_SITE=1`: its daemon belongs to the account the Studio runs as, and a viewer acting there would act as that account. With sign-in on, the Code page shows a person only the sessions there the Studio started for them, and Approve and Deny refuse any other (see *Code page without the platform*).

*Routes.* `GET /api/agent-sites`, `GET /api/agent-sites/<site>/status`, `GET` and `POST /api/agent-sites/<site>/sessions`, `GET /api/agent-sites/<site>/sessions/<id>`, and `POST .../goal`, `.../steer`, `.../approvals/<approval>`, and `.../interrupt`.
