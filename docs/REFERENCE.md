# Reference

The details behind the user guide ([`HELP.md`](HELP.md)), by part of the app. The assistant reads this too.

## Chat

- Replies can show things inline: images, document pages, a workflow's steps as an interactive diagram, and an interactive 3D model.
- **Scope** sets the library the conversation searches (one library, or all of them) and limits its retrieval to the chosen labels; both are enforced on the server.
- The assistant recommends workflows from the account's catalog, checks a run with a dry run first, and launches it only when asked. It lists and inspects runs, including their errors and the end of their logs.
- When it launches work on an HPC system it reads the site's partitions, walltime limits, and saved configurations from the platform, and follows the run to the end. If the platform's per-user workspace has shut down while idle, a launch starts it and tries again.
- An attachment is filed into the library and indexed, and its content, including text read from images, is part of the conversation. Clicking its tile later opens the file in the Library.
- The **/** list filters as you type; the arrow keys move, Enter or Tab inserts, and Escape closes. `/skill_name` applies a skill, `/tool_name` runs a tool, `/agent_name` adopts an agent file for one message, and `/help` lists them all.
- The thinking line above a reply expands to show the reasoning and each tool call as it happens, and stays with the message afterward. While the reply streams, the thinking stays one line until clicked, and each tool call is one row, its result summary beside its name, so nothing opens or closes on its own as the answer arrives.
- A user message with no reply under it, in a conversation that nothing is answering, shows that no reply was saved, with **Retry**: the Studio restarted mid-turn, or the turn failed or was stopped before any text. A turn that is stopped or fails keeps the text and the tool calls it had, so their errors stay readable.
- When a platform tool's command is refused for its credential, the assistant is told whose credential failed (the user's key, or the deployment's when the user has none) and that the fix is a current key under Settings, "Model access", not a change to the command.
- A reply may spend up to 50 model rounds calling tools (Settings, Assistant tools, "Most tool rounds per reply", 5 to 200; `STUDIO_MAX_TOOL_ROUNDS` sets the deployment default). At the limit the assistant answers from what it gathered and says it stopped, and asking it to continue picks up from there. Each reply logs its timing (rounds, tool calls, model time, tool time, time to the first model answer, and per round the time and the characters sent and written) as `reply timing` in the server log.
- A reply sends the model only the tools it needs. The knowledge base tools, skills, and custom and remote tools always go; the workflow and HPC tools, the agent tools, and the file-writing and labeling tools go when the question names their subject or the conversation used them, and the model can add a group itself with `more_tools`. The system prompt's workflow catalog and HPC guidance go with the workflow and agent tools. On a question about every in-process proposal, this cut a reply from about 42 to about 30 seconds with the same model and the same answer.
- The reader's **+**, **Tools** switches (`GET /api/chat/tool-options`: knowledge base, each tool group, extensions, each attached MCP server) arrive with each request as `tools`. A group switched off is not sent, not offered by `more_tools`, and not added by the question's wording; a call to a tool switched off does not run, and the model is told why. A request without `tools` gets every tool, as before.
- A message sent while a reply is running goes to that reply (`POST /api/chat/steer`), which takes it in as a user message before its next model call and notes it in the reply; once taken it leaves the chat's queue. One the reply does not reach, or one with attachments, goes out from the queue afterwards.
- `run_workflow` takes the workflow, the system name (`resource`), and inputs by plain name; it places each input where the workflow declares it, and fills an empty scheduler account, QoS, or partition from the user's most recent completed run on that system (the same workflow's runs first), saying which run the values came from. A dry run says that nothing ran and how to launch.
- `read_kb_file` reads up to 25 files in one call (`paths`), each under its own heading, so a question over many documents takes fewer model rounds.
- `list_storage`, `start_cluster`, `resume_cluster`, `stop_cluster`, `destroy_cluster`, and `cancel_workflow_run` call the platform API with the viewer's key, under the names and descriptions the platform's own web chat uses. `list_storage` returns each item's name, display name, category, type, owner, cloud, region, size, status and its description, whether it is attached, URI, and group, and nothing else. A result is capped at 16 KB, and a refused call returns the platform's own message. The cluster tools take `clusterName` and an optional `user`, which is the viewer's own username when left out; the organization in the path comes from the viewer's platform account, never from the model.
- A long reply folds behind **Show more**, except the latest one, so opening a conversation ends on the last line of its answer.
- In a conversation of six or more messages, a column of ticks along the thread's left edge marks each message. Pointing at a tick previews the message; clicking it scrolls there.
- A model whose provider has locked or rejected its key shows **[locked]** or **[unavailable]** in the model list, with a notice above the conversation. Settings, "Model access" has the unlock link and **Re-check**.
- Under Settings, "Model access", a key you add is checked and the page shows which models it reaches. A deployment can require a personal key; until one is added, chat and models wait while browsing, search, and adding material stay open.
- **Select chats** selects conversations by click, or a range with Shift-click, and deletes the selection after a confirmation.

### Changes that ask first

`start_cluster`, `resume_cluster`, `stop_cluster`, `destroy_cluster`, and `cancel_workflow_run` change something on the platform, and each call waits for the user's approval. Their descriptions tell the model so.

- When the model calls one, the server does not run it. It records the call (the conversation, the tool call id, the tool, its arguments in a canonical form with the owner filled in, a hash of the tool's definition, and the viewer) in `held-tool-calls.json` beside the index, stores the reply with the call marked waiting and an approval request, and ends the reply there. The chat draws the request with the chat package's approval block: the call as it will run, **Yes, allow this call**, **No, deny this call**, and a denial with a note. For `stop_cluster` and `destroy_cluster` a button under it runs the other with the same arguments.
- The answer goes back on `POST /api/chat/stream` as `resume` (the message, the tool call id, allowed or not, and an alternative's name). The server runs only what it recorded for that call: the request never says what to run. It refuses, and runs nothing, when the answer comes from anyone but the viewer the call was held for, names other arguments, names a tool the hold does not allow in its place, arrives after the hold expired (30 minutes; `STUDIO_APPROVAL_TTL_MS`), or the tool's definition changed since. A hold is taken out before its call runs, so an answer runs one call once. A denial tells the model the user declined, with the user's note if they wrote one.
- The result goes into the stored message that asked, with the decision and who made it, and the reply continues from where it paused as a new message under that one.
- One call is held per round of tool calls; another change asked for in the same round is refused with a note to call it again after the answer.
- These tools are offered only to a person present who can approve them: a verified user with their own platform key (on a standalone deployment, the deployment's credential), in their own conversation, with a platform configured. Someone else opening the conversation sees whose answer a request waits for and no buttons. They are never offered to the OpenAI-compatible endpoint or to MCP clients, where nobody can approve a call, and a call that reaches them from anywhere but an approved hold does not run.
- They are their own switch in **+**, **Tools**, "Platform changes", marked as asking first, and in Settings, Assistant tools, each is marked "Asks first" and can be turned off.

## Library

- **Indexed text** shows exactly what the index holds for a file; for an image that is the text read from it plus a description written by a model.
- **Find** highlights every match, stays in view while you scroll, and steps through matches with Enter, Shift+Enter, or its buttons. A file opened from a search result opens on its first match with the query already in the find bar; a PDF or office document opened that way opens on its indexed text, since page images cannot be searched.
- The right-click menu has Open, Labels…, and Delete for a file, and New folder inside…, Labels…, and Delete folder (with its contents, after a confirmation) for a folder. Delete removes the material and its index entries together. In a read-only library, New folder, Rename, Cut, Paste and Delete are disabled with the reason on hover, as are the selection's Move to… and Delete…, the viewer's Delete, and **+ Add**; Labels… is not.
- **Previews.** A PDF's **Pages** and an Office file's pages are images from `GET /api/kb/pdf-info` and `GET /api/kb/pdf-page`, which need poppler and, for Office files, LibreOffice; another library's are cached under its id. Without them, `GET /api/kb/office-preview?path=` reads a .pptx, .docx, .xlsx, .odp, .odt or .ods itself and answers `{ kind: "slides" | "document" | "sheets", ... }`: each slide's title and its paragraphs (with their level), tables and pictures; a document's headings, paragraphs, list items, tables and pictures; each sheet's first 200 rows and 30 columns. Pictures (PNG, JPEG, GIF, WebP, BMP) come from `GET /api/kb/office-media?path=&name=<member>`, only for media members of the package. The viewer names the tab **Slides**, **Document** or **Sheets**. A file with neither (a 97-2003 one, or a page image that fails to load and no outline) loses the tab and opens on its indexed text with one line saying a preview needs LibreOffice.
- With All libraries selected, a `DELETE /api/kb/file` goes to the file's own library (`library=<id>`, the path inside it); the server also takes the combined path with `library=all`. An action on files that names `all` where one library is needed answers 400 saying it works in one library at a time.
- Panes resize at their edges and collapse from their headers.
- A read-only library says so beside its name in the picker. Settings, "Libraries" lists each library with its index and source paths, connects an existing index, or builds one of a folder on this computer or on a remote system over ssh or pw ssh ([`LIBRARIES.md`](LIBRARIES.md)). `GET /api/user-libraries` adds `pwOffered` and `pwWhy` (why pw ssh cannot be used yet), and `GET /api/user-libraries/pw/systems` lists the systems pw ssh reaches as `{ usable, why, systems: [{ name, label, status, running, type }], error }`, running first.
- On the Library page the status panel's Details card describes the folder or file last clicked in the tree, or with nothing clicked the library itself, from `GET /api/kb/details?path=<path>&library=<id>`: one aggregate `gufi_query` over the folder for its size, files, folders, latest change, and largest types, one for the labels below it, and for a file its entry in its folder's index. A library on another system is counted as a whole only with `count=1` (the card's **Count size and types**); until then the card has its connection test's files and folders and `counted: false`. Counts are kept until the index changes (an index job ends here, or a remote library's index time changes), ten minutes at most here and an hour for a remote library; the whole answer is kept 20 seconds on the server and 30 in the page. With All libraries a path starts with its library's id, and nothing is asked until something is clicked.

## Search

- Words match whole words: TIN matches the word TIN, not "routine". "Quotes" match a phrase, OR separates alternatives, -word or NOT word leaves a word out, and word* matches words that start that way.
- Results by meaning are left out for identifiers, acronyms, quoted phrases, and searches using these operators, where a "similar" document would look like a wrong answer.
- A result opens on its first match, with the query in the viewer's find bar.
- Hover a result to tick it; **Select all** and **Labels…** label the whole result set at once.
- **Load more matches** extends a search to 1,000 results.
- Across all libraries, search runs each library in parallel and merges the results. Settings, General, Indexing, "Search across libraries" switches it to `gufi_vt`, as Query uses: name matches, and full-text matches where every search word is plain letters and digits, then run as one `gufi_vt` statement per kind, shown in the GUFI commands panel, while a word with punctuation, a library `gufi_vt` cannot reach, and results by meaning still run per library. Both ways return the same matches. `gufi_vt` answers its libraries one after another, so the parallel default is faster. The environment variable `STUDIO_SEARCH_ENGINE=gufi_vt` sets the default for a deployment.
- In the parallel default each library has 20 seconds to answer (`STUDIO_SEARCH_DEADLINE_MS`). One that has not is left out and `GET /api/search` names it in `slow`; choosing that library alone waits for it.
- Scope (`server/src/libraryScope.ts`): `GET /api/search`, `POST /api/query` and `POST /api/query/sql` take `library` as one id, `all`, or several ids, as a list in a body, a repeated query parameter, or ids with commas (`library=a,b`). Ids are taken once each, in order; `all` among them means all; an id that names no library answers 404. One id alone is asked as before; among several, a library with nothing to answer from is named in `omitted`, as with `all`. Query over several runs on `gufi_vt` exactly as over all. The Search and Query pages keep their own choice in localStorage (`ade-scope-search`, `ade-scope-query`: `"all"` or a list of ids), starting from the Library page's choice; a choice of every library is stored as `"all"`.
- Refined search (`server/src/refine.ts`, `onePassStages` in `server/src/gufi.ts`): `GET /api/search?name=&text=&match=any|all` in place of `q`.
  - `name`: words match any part of a file's name or a folder below the library's root (case-insensitive LIKE, a word of three letters or fewer starting a word); a pattern with `*` or `?` matches the name, or the path below the root when it has a slash (`LIKE ... ESCAPE '\'`, with `%` and `_` escaped); OR separates groups, and -word or NOT word excludes.
  - `text`: an fts5 MATCH expression as given, checked before the search runs (`fts5` in `node:sqlite` where this Node has it, and quotes, brackets and operators at the ends by hand), answering 400 `The text search cannot be read (...)` with how to quote a word with punctuation. The phrase searched by meaning is the text with fts5's operators, quotes, brackets, prefix stars and column filters taken out; it is searched by meaning when `wantsSemantic` would search it.
  - `match=any` (the default): name and folder matches from `name`, word matches from `text`, meaning from the phrase, each kind to its own limit (names and folders `min(max(10, limit/5), 50)` each, words `limit`, meaning 10), and the answer holds all of them, so names never crowd out the rest.
  - `match=all` with both fields: no name rows; every statement that reads words (the Studio's `words`, `ext_bm25_by_file`) or vectors (`ext_vectors_by_file`, the Studio's `gvec`) carries the name filter, inside the same directory visit. The Studio's vectors are then scored as `vec_distance_l2` over the kept files' chunks, the distance vec0's nearest-neighbour search reports for these unit vectors, rather than taken from vec0's nearest neighbours before the filter. Meaning searched the earlier way, for an index from before the current model, is filtered by the same rules (`namePathMatches`). With one field empty, `all` behaves as `any`.
  - A refined search always runs in the walks, whatever "Search across libraries" says.
  - The page puts the search in its address, `#view=search?q=` or `?name=&text=&match=all`, with `in=` naming the libraries when not all, and runs it on arrival.
  - `search_kb` takes `name`, `text` and `match` beside `query`, and `library` as ids with commas.
- A remote host whose login runs only `gufi_query` (`server/src/remoteExec.ts`): when the session loop is refused there (no bash, a restricted shell, a forced command), the site is marked direct and each command is its own ssh call over the shared connection, the program name bare and each other argument a POSIX shell word; only `gufi_query` and `gufi_sqlite3` are sent, and anything else answers 409 `<host> runs only gufi_query for this login (no shell), so this cannot run there.` The connection tests (`POST /api/user-libraries/ssh/test`, `.../pw/test`) answer `shell: false` there, the library is saved with `shell: false` and `gufiBin` `''` when `gufi_query` runs from the login's PATH, and a build check answers its ssh step with "This host runs only gufi_query: connect existing indexes read only; building an index there is not available." A connected index whose top levels have a `words` table is saved with `fullText`, so search reads its words. On macOS the run loop passes on a `KRB5CCNAME` the login shell sets, for ssh with Kerberos. Details in [`LIBRARIES.md`](LIBRARIES.md).
- SSH options per library over ssh (`server/src/remoteExec.ts` `parseSshOptions`): `sshOptions` on `POST /api/user-libraries/ssh/test`, `POST /api/user-libraries/ssh` and the ssh build routes, typed as one line (`-J`, `-p`, `-i`, `-l`, `-F`, `-o Keyword=value` from an allowlist, `-4`, `-6`, `-C`; no spaces, quotes or backslashes in a value), answered 400 `ssh options: ...` with the reason when refused. They are kept with the library as argv, carried in its site (`ssh://dest[:port]#<base64url of the argv>`) and checked again on every use, and go first on every ssh it makes. `PUT /api/user-libraries/:id/ssh-options` with `{sshOptions}` changes them on a connected index after a connection test with them passes. List entries carry `sshOptions` (as typed) and `jump`. The test's ssh step names the jump host, from the options or from `ssh -G`.
- Where an ssh library lands (`reachedHost` in `server/src/remoteExec.ts`): `ssh -G` with the library's options and port, which reads `~/.ssh/config` and connects nowhere, gives the user, host name, port, jump hosts and proxy command, kept ten minutes per site. Libraries whose answers match and whose SSH options are the same (`optionsTag`, a hash of the options with each `-o` keyword in lower case) are one host for search walks and `gufi_vt` locations, so a library typed as `user@host` and one typed as a Host alias for the same account are walked once, and two with different options are walked and queried apart, each with its own options. The list and `GET /api/user-libraries` entries carry `reached` (`user@host`), which Settings shows as the host before an index path; it is null until ssh has answered once. The shared connection's `ControlPath` ends in ssh's own `%C` (a hash of the same host, port, user and jump), followed by `-` and the 8-character `optionsTag` when the library has options, so such libraries share one socket too, and a library with options never rides on a connection opened without them; where the socket folder is too long for that name, the name is 12 hex characters of the site instead.
- Shared ssh connections stay open `STUDIO_SSH_PERSIST` seconds after their last session (default 600, at most 86400; 0 closes with the last session). `POST /api/user-libraries/warm`, which Search and Query call as they open (at most every two minutes), opens each of the viewer's ssh hosts' connections with `ssh -N -f` when none is open (`ssh -O check`), at most once a minute per host, and answers `{hosts}` without waiting.
- No library drops out silently (`server/src/omissions.ts`). `GET /api/search` and `POST /api/query` carry `omitted` when any library in scope was left out, or searched only in part: one entry per library, `{ id, label, reason, partial }`, `partial` false when it added nothing. The reasons: `being built; searchable once its first pass is done`; `its build failed: ...`; `not indexed yet`, for the main folder before its first build (an empty index folder does not count as an index; the main folder is indexed once its index has a `db.db` at the root); `index not found`, for a library built before whose index is gone; `words not searched yet: its text is being read`, or `words not searched: its index has no text yet` (a library built at a depth that reads text whose index has no `words` table yet); for a search by meaning, `not searched by meaning yet: its text is being read` or `not searched by meaning yet: meaning is still being computed` while a library at a Meaning depth is built (meaning runs last), and `not searched by meaning: its index has no vectors yet` after; `did not answer within 20 s`; `not reachable over ssh: ...`; `search failed: ...`; on macOS `macOS has not allowed ACTIVATE Studio to read <folder>; allow it in System Settings, Privacy & Security, Files and Folders (or Full Disk Access)` (elsewhere `permission denied reading <folder>`), with `; results are from its last pass` when its index still answers; and `a folder could not be read (...)` or `N folders could not be read (...)` for folders inside it. Query names a library with no extracted text when the query reads the `words` table (`its index has no extracted text, so text conditions match nothing there`). A library with nothing to answer from is not asked: across libraries it is in `omitted` and in Query's `failed`; asked alone, Query answers 409 `<label> cannot be queried: <reason>`. The Search and Query pages show one line above the results, each name opening its row in Settings, Libraries, and `search_kb` ends its answer with the same list. An index connected as it is, without text, is searched by name and metadata and not named.
- A search runs one walk of a library's index for every kind of match it can find there (`walkSearch` in `server/src/gufi.ts`), the one-pass pattern GUFI's authors recommend: one aggregate `gufi_query` (`-a 1`) whose per-directory step (`-E`) adds, while that directory's database is open, the name matches, the files below a folder whose path matches, the Studio's word matches (its fts5 `words` table) and its nearest passages by meaning (its vec0 `gvec`, with the query's embedding passed in `-I` as a blob literal, one copy per thread), each into one per-thread table that the merge (`-J`) gathers and the final step (`-G`) ranks. The statements run in that order, names and paths first, so a directory without a `words` or vector table answers what it can: the step that needs the missing table fails there and only the steps after it are skipped. No empty tables are written to make every directory alike (an empty fts5 table adds about 20 KB to a directory's 48 KB database, and empty vector tables 40 KB more, as measured). `--no-print-sql-on-err` keeps each such failure to one short line, and only the last 16 KB of `gufi_query`'s error output is kept. gufi_query compiles every statement again in every directory, so there are four at most: one trim that keeps each kind's best, then one insert per kind of table read.
- On a synthetic index of 24,000 directories and 100,000 files, with words in a quarter of the directories and vectors in a tenth, a search took about 2.9 s before (the name and word walk, about 0.8 s, beside the search by meaning, which walked the tree for databases with vectors and then attached each one, about 2.9 s) and about 1.0 s in one walk. Without vectors in the index the walk takes about 0.85 s; names and words alone, as before, about 0.7 s, and the folder-path matches add about 0.15 s. Timings on a shared host, median of five.
- Results are fused with reciprocal rank fusion (`fuseRows`): each kind is ranked on its own (words by `bm25`, vectors by distance, names by how closely they match, folder-path matches by how near the matching folder is), each file once per kind, and a file's score is the sum over the kinds that found it of 1 / (60 + its rank in that kind). The final step of each walk computes the same order for its own rows; across libraries and walks the Studio fuses them again the same way. Ties go to the more exact kind (words, then name, then folder path, then meaning), then the path, so the order is the same on every run. A hit is labelled by its most exact kind (`mode`: `fts`, `name`, `path` or `vector`) and lists all of them (`kinds`); `score` is its fused score. `bm25` is computed within each directory's table, so word scores from two directories compare roughly; vec0 distances for unit vectors compare exactly.
- Folder-path matches compare the path below the library's root, never the index's own folders, with the same rules as names (a term of three letters or fewer must start a word, here also after a slash). A file whose name matches is a name match only.
- Meaning comes from the same walk for directories embedded with the ONNX model (`gvecmodel` `minilm-l6-mean-int8`, with or without a `-t<N>` truncation). A library whose walk returns no passages by meaning while its index has vectors (embedded with the earlier GGUF model, say) is searched by meaning the earlier way, through `gufi_sqlite3`.
- External databases in the shared text and vector schema are read in the same walk with `--external-copy`. In each directory, each file other than `db.db` whose name matches `STUDIO_EXTERNAL_DB_PATTERN` (default `\.db$`; empty turns it off) is attached, and its best text (`ext_bm25_by_file`, an fts5 table, by `bm25`) and, where `vector_model_name` names a model whose query vector the Studio has (all-MiniLM-L6-v2, which the ONNX model quantizes), its nearest chunks (`ext_vectors_by_file`, by cosine distance, put on the scale of vec0's distance for unit vectors) join the same table. Rows are matched to the directory's entries by `binode` and `bmtime`, so a file changed since its text was extracted is not matched. So an index carrying those databases is searched by text, and by meaning for that model, with no Studio enrichment, and a library's "words not searched" note is withdrawn when its external databases answered. A GUFI that does not know `--external-copy` or `--no-print-sql-on-err` (from before 2026) is asked again without them.
- On a rolled-up index, the walk does not visit the directories rolled into their parents, so their own tables (the Studio's words and vectors, external databases) are not read there; names and paths are. The Studio does not roll up the indexes it builds.
- Libraries on the same remote host and account share one walk (the account and host are where ssh lands, from `ssh -G`, below): their index roots go to one `gufi_query` in one remote command, so a search across them is one round trip, and each row goes back to its library by the root it is under. Before, each library on another system ran one remote command for names and words, and none for meaning. A walk that does not answer in its 20 seconds names every library in it. Several local index paths in one `gufi_query` measured no faster than a run each at once (about 0.84 s either way for four libraries of 6,000 directories), so libraries on this computer keep a walk each with its own deadline; `STUDIO_STACK_LOCAL=1` stacks them too.
- Local `gufi_query` runs use one thread per core up to 16; a remote system's use its own processor count up to 16, or `STUDIO_REMOTE_THREADS` ([`LIBRARIES.md`](LIBRARIES.md)).

## Status panel

The Model card shows only while AI features are on. The Connections card shows only when there is something to list, grouped as the ACTIVATE platform, attached MCP servers, and the machines that hold remote libraries.

While open and the tab is visible, the panel reads `GET /api/tasks`, `/api/fleet`, `/api/runs`, `/api/index/status`, and `/api/settings/mcp-servers?cached=1` every 10 seconds, all answered from the Studio's own state, and `GET /api/sessions` and `/api/user-libraries`, which can reach the platform, once a minute. ## Query

- **Presets** fill the builder and run it: biggest files, oldest files, changed in the last 7 days, largest directories, and totals by extension and by owner. Each is the overall top N across directories and libraries: every directory keeps its own top N (`-E`), and `-G` orders the merged rows; across libraries the outer `ORDER BY` or the Studio's merge does the same. A query saved as one of the former canned queries (`canned` in its payload) opens as the builder form that runs it; `POST /api/query` still takes `canned`, which the chat tool uses.
- **Builder**: condition rows, matched all (`AND`) or any (`OR`, `builder.match: "any"`), plus grouping (none, extension, directory, owner), sorting, a limit, and a folder to search under. **Reset** clears the form and the results; **Show SQL** shows what the form compiles to. Each field takes its own conditions, and the server refuses others with a 400 naming them:
  - name, path, extension, owner: contains, does not contain, equals (name also greater and less than). Path is relative to the library: equality compares the whole path, contains looks only below the index's own folder. Owner is GUFI's `uidtouser(uid)` on the host that runs the query.
  - size: equals, greater than, less than, in bytes or with a unit (`10 MB`, `1.5G`, `500k`; powers of 1024).
  - modified: on, after, before (`eq`, `gt`, `lt`) a day (`2026-01-01`), a minute or second (`2026-01-01 09:30`), or a time ago (`7 days`, `12 hours`, `2 weeks`), in UTC as results show times. On is within that day or minute, after is at or after its end, before is before its start. The server works out the seconds: GUFI's own `strftime(format, seconds)` takes the place of SQLite's, so SQL cannot parse a date.
  - text: matches the words, a subquery on the `words` table, so it can stand beside other conditions joined by OR. A directory with no `words` table answers nothing for a text condition, and under any, nothing for its other conditions either.
  - label: equals or contains, directory labels included.
  - Directories take name, owner, size (`totsize`) and modified conditions.
- **SQL**: any read-only SELECT over the index tables.
- **Across libraries**, a query runs as one `gufi_vt` statement: a virtual table per library, a library on another machine as a `remote_cmd` location, unioned with the overall order and limit outside. Libraries on one host, reached the same way and asked the same plan, share one location with an `index=` per root, so the host runs one `gufi_query` (and one check) for all of them, and each row goes back to the library its path is under; raw SQL is not stacked, and `STUDIO_STACK_REMOTE=0` stacks nothing. `POST /api/query` answers `engine: "gufi_vt"`. The Studio merges the libraries' rows itself instead (`engine: "merge"`, the same rows, with `mergeReason` saying why) when this GUFI's `gufi_sqlite3` has no `gufi_vt` with remote locations, when the query's SQL holds a double quote outside a string (a quoted identifier, a comment), when a library's path cannot be given to `gufi_vt`, or when the `gufi_vt` statement fails. `gufi_vt` takes each SQL stage as a double-quoted value read verbatim, so a double quote inside a string, such as the phrase quotes of a text condition's FTS5 `MATCH '"a" AND "b"'`, is written for it as `'||char(34)||'`, which gives the same string; text conditions therefore run through `gufi_vt` too. Paths with spaces can: `gufi_vt` starts `gufi_query` and the remote command with `execvp`, never a shell, and strips only a value's outer quotes, so the Studio single-quotes each path, or double-quotes one holding a single quote, as the macOS app's paths need (`ACTIVATE Studio.app`, `Application Support`). A path holding both kinds of quote, or a line break, cannot be given. A remote library's index reaches the wrapper unquoted at the end of the command line `gufi_vt` builds, so it may hold single spaces but no word of it may start with a quote.
- **Saved queries** rerun in one click; a new deployment comes with a few examples. The code button beside one shows the SQL of each `gufi_query` stage it compiles to (`-I` and `-K` create a table for each thread and one for the result, `-E` runs in every directory, `-J` adds each thread's rows to the result, `-G` orders and limits it; raw SQL is `-E` alone) and the command that runs it, each with a copy button. It reads `POST /api/query/sql`, which takes the body `POST /api/query` takes and answers `stages` (`flag`, `sql`) and `commands`, one per library in scope as a run would record them, without running anything.
- Result rows with a path can be ticked and labeled, as search results can.

## Labels

A file's own labels show green in the viewer, and labels it inherits from a folder show gray.

- The knowledge base keeps labels on its files, as the `user.studio.tags` xattr (or the label overlay where the filesystem refuses xattrs), and in the index built from them.
- Every other library's labels are kept by the Studio in `INDEX_BASE/libraries/<id>/labels.json`, keyed by the path in the library, so a read-only folder or an index on another machine can be labeled without changing it. An entry is that path's own label and is inherited by everything below it. They are not written into the index in GUFI's external database form (the way the knowledge base's extracted text is, as a `words` table in each directory's db): a read-only or remote index cannot be written, and an external database is found through the index's own directories. So search, the tree, Details and the vocabulary merge them in by path, and a Query label filter on that library compiles them into its SQL: files as `path IN (...)` and labeled folders as path prefixes.
- `GET /api/kb/tags?path=&library=` answers `{ own, inherited, stored }`, where `stored` is `files` or `studio`; `POST /api/kb/tags` (`{ paths, add, remove }`) applies in each path's library, so with `library=all` one request may span libraries, and answers `{ updated, stored }`. `GET /api/tags` counts both kinds.
- Labels of a library on this computer whose files are gone are dropped at most every ten minutes, never when every labeled path is missing at once (an unmounted folder), with a backup kept beside the file. A remote library's are not pruned. Removing a library removes its labels.

PNG, JPEG, SVG or WebP, told by the file's first bytes rather than its name, at most 1 MB: over that is a 413, anything else a 415, and a body that is not multipart a 400. Answers the `branding` state.

With a launcher it saves `KB_ROOT` to the launcher's settings file and restarts: `{saved: true, restarting: true}`. A settings file without a restart answers `{saved: true, restarting: false, note}`; no launcher answers `{saved: false, restarting: false, note}`, naming the `KB_ROOT` to set.
- `POST /api/setup/port {port}`: a whole number from 1024 to 65535; the Studio and its MCP endpoint (`/api/mcp`) share it. With a launcher it saves `PORT` to the launcher's settings file and restarts: `{saved: true, restarting: true, port}`. A port something else listens on is a 409, as is any change while a setup index build runs. A settings file without a restart answers `{saved: true, restarting: false, port, note}`; no launcher answers `{saved: false, restarting: false, port, note}`, naming the `PORT` to set. - `POST /api/setup/complete`: saves `setupDone`. Finish and Finish later both send it, so setup does not open on its own again.

The wizard opens over the app on a first run, and on the `ade:setup-open` event: Settings, General, Run setup again sends it, as does the address `#view=settings:setup` (the macOS app's Run Setup… uses it), which then shows Settings, General. ## Indexing

Every change to the main folder's index is a job, and jobs run one at a time: a whole-folder build, one folder after an upload or an edit, and the background sync. Each job has four phases, each with its own count:

| Phase | Program | Counts | Searchable after it |
|---|---|---|---|
| `names` | `gufi_dir2index -n <threads>` | folders | by name, on a first build |
| `documents` | `server/dist/preextract.js --jobs <threads>` (downmark) | PDFs and Office documents | |
| `text` | `indexer/enrich.py --jobs <threads>` | files to read (images, other formats), then folders whose full-text table is written | by text |
| `meaning` | `indexer/embed.py --jobs <threads>` | passages to embed, then folders whose vector table is written | by meaning |

Each phase runs its work side by side: a process per document or image, a few embedding processes sharing the thread count (at most eight, with several ONNX Runtime threads each), and the per-folder databases written with `synchronous=OFF`, since the index can always be rebuilt from the files. A first build swaps the names in as soon as they are read, so search by name works while the rest follows; a build over an existing index works on a copy (`INDEX_DIR/gufi.staging-<id>`) and swaps it in at the end, so search answers from the old index meanwhile. One folder is built aside the same way and swapped in when done.

The background sync finds what changed by reading the time of every folder and file, on a worker thread (`server/src/dirScan.ts`), so the server keeps answering while it walks a large folder.

Text is cached in `INDEX_DIR/extract` by file and date, and embeddings in `INDEX_DIR/embed-cache.db` by the hash of the model and the text embedded, so a rebuild reads and embeds only what changed. A whole-folder build drops embeddings nothing uses any more. A program that writes nothing for 30 minutes is stopped and the job fails.

Embeddings come from all-MiniLM-L6-v2 through ONNX Runtime (int8, mean pooling; model id `minilm-l6-mean-int8`) when `indexer/embed_onnx.py` can import onnxruntime, tokenizers and numpy and `INDEX_BASE/models/minilm-l6` holds `model.onnx` and `tokenizer.json`; otherwise from the GGUF model through sqlite-lembed (`minilm384`). `embed.py --backend onnx|lembed` forces one, and `--max-tokens 128` cuts each passage at 128 tokens rather than 256, for about 40 percent of the CPU and slightly lower ranking (its vectors are marked `minilm-l6-mean-int8-t128`). Each folder's `db.db` names its model in a one-row `gvecmodel` table; a folder without one holds `minilm384` vectors. An index embedded with the older model keeps answering by meaning until it is embedded again: a full build does that, and so does the first pass over any of its folders, which widens to the whole index so the index never mixes models. Searches embed the query with the index's own model; for the ONNX one, a Python worker (`indexer/embed_query.py`, JSON lines on stdin and stdout) is started at the first such search, kept for ten idle minutes, and ends with the server. `indexer/fetch_embed.py` installs the packages and the model, as pinned with their SHA-256 in `indexer/embed_deps.json` (Linux x86_64 and aarch64, macOS arm64; Python 3.11 to 3.13): `--deps DIR` for the packages, into `indexer/.deps` for a clone (`--no-readers` leaves out xlrd and olefile), and `--model DIR`; `--download --platform P --cache DIR` only downloads the wheels for P and the model into DIR, for another system. `indexer/setup_gufi.sh` runs it. A build on a remote system embeds with the same model, sent there with its packages for the Python there and installed once in `~/.activate-studio/embed/<version>` (`server/src/remoteEmbed.ts`, [`LIBRARIES.md`](LIBRARIES.md#indexes-built-on-a-remote-system)).

**Folders used before.** The index records which folder it is of (`INDEX_DIR/indexed-root`). When the main folder changes, at the next start the old folder's index and caches are put aside in `INDEX_DIR/folders/<hash>`, the three most recent kept, and a folder with an index put aside gets it back: its next build updates that index instead of building one from nothing, and the sync picks up what changed since. `GET /api/setup/status` reports `primary.earlierIndex` while one is kept for the folder in use and not yet back.

**Routes.**

- `GET /api/index/status`: the one status every view reads. `running` (a job runs or waits), `job` (the running job), `queued`, `last` (the last job to finish this server start), `lastBuild` (the last whole-folder build or delete of this folder, kept across restarts in `INDEX_BASE/index-runs.json`), `runs` (the last ten jobs), `indexed`, `incomplete` (the last build was stopped or failed), `threads`, `folder`, `indexDir`, `log` (`path`, `bytes`, `reveal`), and the sync's `lastSweepAt`, `lastSweepMs`, `lastChanges`, `lastError`, `sweepIntervalSec`.
- A job: `id`, `kind` (`build`, `folder`, `sweep`, `delete`, `move`), `dir`, `label`, `state` (`queued`, `running`, `done`, `error`, `cancelled`), `startedAt`, `runningAt`, `finishedAt`, `ms`, `error`, `threads`, `phases` (each `id`, `label`, `state` of `pending`, `running`, `done`, `skipped` or `failed`, `done`, `total`, `unit`, `step`, `ms`, `note`), `searchableAt`, `warnings` (the first files that could not be read) and `warningCount`, and `progress`, the summary pages written before phases read (`phase` is `directories` while a phase runs, `current` names it, with its `done` and `total`; then `done`, `error` or `cancelled`; `failed` lists folders a sync could not index).
- `POST /api/index/build`: build or update the whole folder; a second request while one runs gets it. `POST /api/reindex` does the same.
- `POST /api/index/job {path}`: one folder, returned at once (an upload's pass); `POST /api/index/dir {path}` waits for it.
- `GET /api/index/job/<id>`, `POST /api/index/job/<id>/cancel`: follow or stop one job. A queued job is dropped; the running one has its programs stopped (their whole process group) and ends `cancelled`.
- `POST /api/index/cancel`: stop the running job and every queued one.
- `DELETE /api/index?confirm=1`: delete the index and its caches (`gufi`, `extract`, `embed-cache.db`, `semantic-map`, previews, the sync's record); the folder's files are never touched. Without `confirm=1` it is a 400. Single-user installs only.
- `GET /api/index/log?lines=N` (default 400, at most 5000), `?full=1` for all of it: the index log as plain text. It is `STUDIO_DATA_DIR/logs/indexing.log` in the macOS app, `INDEX_BASE/logs/indexing.log` elsewhere, one previous file kept past 10 MB. `POST /api/index/log/reveal` shows it in the Finder on a Mac.
- `GET /api/index/extractors` (`?fresh=1` looks again): `extractors` (each `name`, `available`, `covers`, `note`, `optional`), `formats` (each `formats`, `readers`, `ok`, `note`) and `missing`, the formats nothing here reads. A reader is optional when another covers its formats, such as pdftotext where downmark's native binary reads PDFs.
- `GET /api/index/settings`, `PUT /api/index/settings`: the main folder's settings, kept per library in `INDEX_BASE/indexing.json` and followed by libraries built of a folder on this computer, each of which keeps its own embedding cache under `INDEX_BASE/libraries/<id>`: `threads` (1 to 256, or `null` for one per core), `depth` (below; the main folder defaults to `meaning-documents`), `pdfReader` (`auto`, `pdftotext`, `pypdf`), `imageDescriptions` (from the `ocr` depth up), `legacyOffice`, `meaningSpeed` (`standard`, the first 256 tokens of each passage, or `faster`, the first 128, which embed.py gets as `--max-tokens 128`; set for the main folder and followed by libraries built here; a change embeds each index again, once, since the two are different models to it). The answer's `documents`, `ocr` and `meaning` follow the depth. What an earlier version saved or sends instead of a depth (a `meaning` level, the on/off `embeddings` before it, and the main folder's `documents` and `ocr` switches, which every library followed) is read and accepted as the nearest stop. The answer adds `cpus`, `threads` in use, `readers`, `ai` (`enabled`, `visionModel`) and `location`.
- `POST /api/index/location {path}`: keep the index and its caches somewhere else (not inside the folder being indexed, nor containing it). Single-user installs with a launcher: the files move there (across disks too), `STUDIO_INDEX_DIR` is saved to the launcher's settings, and the Studio restarts. An empty path goes back to the default, `INDEX_BASE`.

**Readers.** Office documents and PDFs convert through downmark, which comes with the server (its native binary per platform reads PDFs and, with tesseract, scanned pages). A PDF it cannot read goes to pdftotext where poppler is installed, then pypdf (the macOS app carries pypdf). OpenDocument (`.odt`, `.ods`, `.odp`, `.odg`) is read by `enrich.py` with the standard library (paragraphs, headings, lists, tables, sheets under their names, slides with their speaker notes, and a text document's headers and footers; comments left out), `.xls` through xlrd (sheets, numbers to 15 significant digits, dates as dates) and `.ppt` through olefile (the text and speaker notes of its slides, masters left out). xlrd and olefile are pure-Python wheels pinned in `indexer/embed_deps.json` (`readers`), which the macOS app and the container carry and `fetch_embed.py --deps` installs (`--readers-only` for those two alone); `enrich.py` also looks in `indexer/.deps`. A file those cannot read, and a `.doc` downmark cannot read, goes through LibreOffice where it is installed and the setting allows (`SOFFICE_BIN`, `soffice` on the PATH, or `/Applications/LibreOffice.app`), each worker with a LibreOffice profile of its own; the same LibreOffice renders Office previews. `GET /api/index/extractors` (`?fresh=1` looks again) and `/api/index/settings` carry the readers report: `extractors`, `formats`, `missing`, and `install` (`platform`, `brew`, `apt`, and `items`, each with `name`, `adds`, and the `command` that installs it on this machine, or a `link` where there is none: Homebrew's page on a Mac without it). The Studio shows these commands and runs none of them. Images are read by tesseract where installed and described by the vision model when AI features are on and one is set (Settings, General, AI features), both from the `ocr` depth up. The macOS app carries its own tesseract with the English model (`Contents/Resources/ocr`, built by `deploy/mac/build_ocr.sh`), which its run loop puts first on the server's PATH with `TESSDATA_PREFIX` naming its data; the readers report shows it as bundled, and poppler's entry then offers only the PDFs downmark cannot read.

- `PUT /api/libraries/:id/depth {depth}`: a library's index depth, for the main folder and libraries the Studio builds (here or on a remote system), kept with its index settings. The main folder and a library built here apply it at their next sync, which the change asks for two seconds later (after a running job, and coalescing several changes); a library built on a remote system, at its next Rebuild, since a remote build always runs whole. The stops, each adding to the one before: `names` (gufi_dir2index only; the documents, text and meaning phases are skipped, and a remote build is sent no enrich.py), `text` (enrich.py with `--no-ocr`, and no image descriptions), `ocr` (tesseract on images and scanned PDF pages where installed, and image descriptions), `meaning-documents` and `meaning-full` (search by meaning, below). A built library starts at `ocr`, the main folder at `meaning-documents`. `PUT /api/libraries/:id/meaning {level}` is what an earlier client sends: `off` takes the depth to `ocr` at most, `documents` and `full` to the meaning stops. An index the Studio only reads answers 409 to both: it stays as it was built. `GET /api/libraries`, `GET /api/user-libraries` and the client configuration carry each library's `depth` and `meaning`, null for such an index. Search looks in a library by meaning only when its meaning is not `off` (or, for a read-only index, when it has vectors), and in the main folder's words unless its depth is `names`.
- A change of depth touches no file, so the sync's look for changed folders would not see it. The depth an index was last built or synced at is recorded (`INDEX_BASE/index-depth.json` for the main folder, kept and put aside with its sync state when the folder changes; `INDEX_BASE/libraries/<id>/depth-state.json` for a library built here): `depth`, `ocr` (the depth reads images and tesseract was found, so OCR becoming available counts too) and `meaningSpeed`. A build writes it. Each sync (`POST /api/index/sweep`, which Sync now calls, and the background one) compares it with the settings: a higher depth runs only what it adds, over the whole index in place with the caches (from `names`, the documents and text phases; OCR newly on, the same, which reads images and converts again the PDFs downmark converted without OCR, marked `(no OCR)` after the version on their cache entry's first line; search by meaning newly on, wider, at another speed, or after new text, the meaning phase, and the semantic map soon after), as a `sweep` job labelled `Applying the new index depth: ...` whose names phase is `skipped` (`unchanged`). The record is written only when that succeeded, so a failed or stopped run is tried again at the next sync. A lower depth runs nothing and is recorded: search stops at it, and text or vectors read before stay until their folder is indexed again. An index with no record, one from before it was kept, counts as built at its settings now. `PUT /api/index/settings` with `depth` (or what an earlier client sends for it) or `meaningSpeed` asks for the main folder's sync the same way, and `meaningSpeed` for each library built here too; with the sync interval at 0 (paused) nothing is asked for.
- The meaning stops reach `indexer/embed.py` as options: `meaning-documents` is `--documents-only --max-chunks 4` (the first four passages of PDF, Office, text, Markdown and image files), `meaning-full` is the default (up to twelve passages of every file with text, markup excepted), and the stops before them skip the phase.

**The semantic map.** `indexer/semantic_map.py` (numpy) reads each folder's passage vectors from sqlite-vec's own tables (`gvec_rowids`, `gvec_vector_chunks00`, the validity bits in `gvec_chunks`) without the extension, averages them per file, fits a PCA on at most 20,000 files and projects every file to three components for the map and sixteen for k-means (4 to 14 clusters, largest first). A cluster is named for its distinctive terms: from each file's passages (`gchunks.ctext`, about 20,000 characters a file, with the words split by a passage's cut taken off: where consecutive passages overlap, the characters around the cut say whether it split a word, which is then whole in the neighbor, and otherwise a word at the cut goes) the 30 commonest words of 3 to 24 letters, without stop words or digit runs; for each cluster, each word's share of its files with text times the word's inverse document frequency over every file of the map, kept where it is in at least 5% of those files (and two, in a cluster of four or more). The name is the best two words, or three where they fit in 26 characters; a word another cluster's name uses goes behind unused ones, and a name already taken takes the next word, so no two read alike. A cluster with fewer than two such words is named for its folders (the folder most of its files are in, then the second, with its parent where both have the same name, as `pw/docs + gs/docs`; clusters that would share a name go a level deeper). Each cluster is linked to the two clusters whose mean vectors (in the full 384 dimensions) have the highest cosine, each pair listed once. Each library on this computer with vectors has a map of its own, made from its index: the main folder's in `INDEX_DIR/semantic-map`, another library's in `INDEX_BASE/libraries/<id>/semantic-map`, removed with the library. An index connected as it is is mapped where it has the Studio's own vector tables (`gvec`); vectors in another schema (`ext_vectors_by_file`) are not read, and such an index, like one with none, has no map. A library on another system is mapped here from its vectors fetched there (`server/src/remoteMap.ts`), with two aggregate `gufi_query` walks over the library's own connection, so a host whose login runs only `gufi_query` answers them. The first counts, per model, the files with vectors and their passages (the Studio's `gchunks` joined to sqlite-vec's `gvec_rowids`, and `ext_vectors_by_file` for all-MiniLM-L6-v2 through `--external-copy`, matched to the directory's entries by inode and mtime), and a digest of the passages' ids and hashes; a few rows come back. The second fetches the files of the model most files use: per file its path, the mean of its passage vectors (added up in SQL with sqlite-vec's `vec_add`, a recursive fold in passage order), that mean's length, the mean normalized and quantized to int8 (`vec_quantize_int8(..., 'unit')`) as 768 hex characters, and, for about 10,000 of them, the first 1,000 characters of their first passage, for naming the clusters. Past `STUDIO_REMOTE_MAP_FILES` files (default 50,000) a sample is taken: the files whose inode hashes lowest (`((inode % 2147483647) * 1103515245 + 12345) % 2^31`), selected in the walk by a threshold a little above the cap's share and cut to the cap here, so the same files come back every time; the map's status line gives both counts ("3,000 of 20,000 files shown (a sample of 5,000 fetched from <host>, made with <model>, <when>)"). The rows go to `vectors.jsonl` in the owner's folder (`INDEX_BASE/users/<owner hash>/maps/<id>`, removed with the library), and `semantic_map.py --vectors <file> --model <model> --of <M>` reads them back (each int8 value at the middle of its step, the mean's length restored) and makes the map there as it does from an index, with `of` in the overview; without numpy the server draws its smaller map from the same file. Measured over ssh to localhost, 20,000 files with 50,000 passages: the count about 60 ms, the fetch 0.8 s for 27 MB of rows (34 MB in the session's base64, 24 MB on the wire with ssh's compression, which the Studio's ssh connections now ask for), the map 1.9 s. The record of the last check (`state.json`: the counts per model, the model mapped, the bytes and time of the fetch) decides the next: a check is the count alone, and the files are fetched again only when the counts or the digest changed. It runs when the map is looked at and an hour has passed since the last, after a build of the library there finished or a connection test found its index rebuilt, and on **Refresh** (`POST /api/libraries/:id/semantic-map/refresh`), which fetches whatever the count says. A file's nearest files are searched for there: its fetched vector is the query, one `gufi_query` walk asks each directory's vec0 table (or `ext_vectors_by_file`, by cosine distance on vec0's scale) for its nearest passages of the same model, each thread keeps its best, and the answers are kept until the map is made again. A GUFI there without sqlite-vec, or a connection that fails, leaves the map it had with the error, or with none a `failed` state to try again; a library there with no vectors is `remote-none`. The script writes `overview.json` (`version` 3; every cluster's `label`, `folder`, `terms`, `count` and centroid `x`, `y`, `z`; `links` as `a`, `b`, `sim`, nearest first; a sample of at most 3,000 files spread across the clusters, at least 25 from each) and `cluster-<c>.json` (all of a cluster's files, in a random order), into a scratch folder swapped in whole. It runs in the background, five seconds after a build's meaning phase embedded anything or pruned the cache (for a library built here, after its build or a new depth with meaning) and at most every ten minutes after a sync's, and once when a map is asked for and there is none; reading never makes one. Without numpy the server draws one itself from at most 4,000 files and marks it `fallback`.

- What each library's index holds (`index`, `fullText`, `vectors`) is found by probing a sample of its databases (twelve, breadth first), and what the sample does not find is counted over the whole tree in the background: one aggregate `gufi_query` counts the directories whose database has the `words` and `gvec` tables (about 50 ms for 1,300 directories), after every build or sync and at most once an hour otherwise. The result is kept in `INDEX_BASE/library-caps.json` with `probedAt` and, once counted, `exactAt`, so a restart reads it before any probe. Search treats a library on this computer as without words or vectors only when that count found none since the tree last changed; until then it looks there (a missing table fails that step in each directory, at no other cost), so a library whose vectors are in a few folders never loses its meaning results to the sample. The same rule decides the notes on what a search or query left out, and what the assistant's list of libraries says each is searched for. A build or sync marks it stale and probes again at once; until the probe answers, and when a probe can open none of the databases it samples, the last known capabilities stand (marked `stale`, with the probe's `error`), never reset to none, and the probe runs again within 30 seconds. At start each library's state goes to the index log in one line: whether it has an index, words and vectors, its depth, its build and when it was built, whether what is known of it is stale, and anything that leaves it out of search.
- A stop (SIGTERM, which a shutdown of the computer sends) ends the programs of every index job and library build. A library build cut off keeps its state, `building` or `updating`, and the next start takes it up: a change of depth (`pending: "depth"`) with a sync of the index it has, and a build or rebuild by building again, which reuses every file the extraction cache already holds (text, PDFs, Office files, OCR and image descriptions, by modification time) and the embedding cache.
- Folders the Studio may not read (EPERM, which macOS answers until it allows the app in Files and Folders or Full Disk Access, or EACCES): the scan of a folder, `gufi_dir2index` and `enrich.py` name them, and they are recorded in `INDEX_BASE/denied.json` for the main folder and `INDEX_BASE/libraries/<id>/denied.json` for a library built here, and named in search and Query. `gufi_dir2index` exits 1 when it cannot open a folder after writing the rest of the tree; when every error it printed is a permission error, the build stands. A sync keeps such a folder as it was last indexed, not taken for removed, and indexes it again once it can be read. Their files are not counted as indexed.
- A source folder its owner may not write (mode 0555, say, on a read-only share or snapshot), as a user other than root (`server/src/indexModes.ts`): `gufi_dir2index` sets each index folder to its source folder's mode as it finishes it, before the folders inside it make theirs, so it left out everything inside a 0555 folder (a `mkdir <index folder>/db.db failure` line for each, and an exit status of 0) and the build failed moving the tree into place. The folder scan before a build or sync (`dirScan.ts`, or the names count for the main folder) lists the folders that lack owner read, write or search, with the folders inside each that this process can open; those index folders are made before `gufi_dir2index` runs, which takes a folder that exists, and after it the locked folders' index folders get `u+rwx`, parents first, keeping their group and other bits. GUFI's record of the source keeps the source's modes. Index trees are removed with `rmTree`, which opens folders when a removal is refused, and a sync opens an index an earlier version built and indexes the folders inside a locked folder that it left out. A `mkdir ... failure` line that remains names the folder as left out, by its source path, in the record above. A build on a remote system runs `gufi_dir2index` again after making those index folders when its log has such lines, and opens the index folders with `find ... -exec chmod u+rwx` before moving the tree.
- `GET /api/kb/semantic-map`: the overview, with `available`, `building`, `files`, `shown`, `clusters`, `points` (`p`, `x`, `y`, `z`, `c`), `model`, `builtAt`; without a map, `reason` (`off`: the main folder's depth stops before search by meaning; `none`; `failed`, with `error`).
- `GET /api/kb/semantic-map/cluster/<c>?offset=&limit=`: a page of a cluster's files (2,000 by default, at most 5,000).
- `GET /api/kb/semantic-map/neighbors?file=<path>&k=5`: the `k` files (1 to 20) of the main folder nearest `file` by meaning: the mean of the file's own passage vectors (unit length) is the query, and every directory whose vectors come from the same model (`gvecmodel`) answers with its nearest passages through sqlite-vec, as a search by meaning does. Returns `neighbors` (`p`, `sim`, the cosine, nearest first, and the file's `x`, `y`, `z`, `c` on the map where it has a place; a map of more than 300,000 files gives none). An empty list with `reason: "none"` where the file has no vectors, `"off"` where the depth stops before search by meaning; 400 for a path outside the main folder. Answers are kept until the map is made again. Maps made before links and word names (version 2) have neither, and the page draws them without links.
- `GET /api/libraries/<id>/semantic-map`, `.../cluster/<c>` and `.../neighbors`: the same for any library (`kb` is the main folder), with `library` (`id`, `label`, `kind`: `main`, `built`, `connected` or `remote`; `depth`, null for an index the Studio does not build; `vectors`). `reason` adds `connected` (an index used as it is, with no vectors the Studio reads) and `remote` (a library on another system); `off` there is a built library whose depth stops before search by meaning, which `PUT /api/libraries/<id>/depth` changes. 404 for a library there is not.
- `GET /api/semantic-maps`: each library's map at a glance (`id`, `label`, `available`, `files`, `reason`, `building`), for the page's picker, which starts on the one with the most files.
- `GET /api/kb/topology` and `GET /api/libraries/<id>/topology?dir=&refresh=1`: a library's folders with their `files` and `bytes`, for the treemap, from one aggregate `gufi_query` run where the index is (on another system over ssh, as `gufi_query` alone, so a host that runs nothing else answers it). Each directory's totals go to its ancestor six levels below `dir` (`levels`), so a folder at that depth holds everything under it and is asked for again, with `dir`, as the page opens it; past 20,000 rows the answer is cut a level shallower. Paths are from the library's top; `root` is `dir`, `ms` the query's time. Kept two minutes for a library here and ten for one elsewhere; `refresh=1` asks again. `available: false` where there is no index.

`indexer/reindex.sh` runs the same phases from the command line, before the server starts: `INDEX_THREADS` sets the threads, `SKIP_EMBED=1` skips embeddings.

## Updates

How the macOS app checks, verifies, installs and rolls back is in [`MACOS.md`](MACOS.md). A Studio is in one of three update modes: `app` (the macOS app, which installs), `clone` (told the newest version and how to update), and `hosted` (sign-in on, or `PW_PLATFORM_HOST` set: no checks, and the update routes refuse with 403).

- `GET /api/updates`: `mode`, `current` (`version`, `builtAt`), `policy` (`check`, `install` `manual` or `auto`, `channel` `stable` or `prerelease`), `latest` (`version`, `publishedAt`, `notes`, `url`), `releases`, `available`, `canInstall`, `reason`, `command`, `state`, `progress`, `error`, `checkedAt`, `previous`, `reopen`. `latest` is the newest release on the channel; for the app, the newest that carries the signed app. `releases` lists every release newer than the running version up to and including `latest`, newest first, each with `version`, `publishedAt`, `url` and `entries` (`title`, `pr`, `body`) parsed from its notes. A release whose macOS build failed is in the list when a later one is installable, since its changes come with it. `command` is the commands that update a clone of the repository (`git pull`, `pnpm install`, `pnpm build`), and null for the app, including an app its user cannot write to. When a check is due (15 minutes since the last one by the clock, or 5 minutes while a new release waits for its macOS build or the release server is unreachable), this request starts it in the background and answers with `state: "checking"`.
- `POST /api/updates/check`, `/install`, `/rollback` answer the same status.
- `GET /api/changelog` (`?after=vX.Y` keeps the versions newer than that): `included` (false when the build carries no change log), `current` (the running version), and `versions`, newest first, each with `version`, `date` and `entries`. It reads `CHANGELOG.md` at the top of the app (`STUDIO_CHANGELOG_FILE` names another). The change log is regenerated after each release, so a build carries it as of the version before its own; in the app and a clone, the notes of saved releases up to the running version fill in what the file lacks. Versions with no entries are left out. It answers in every mode.
- Release notes and the change log share one format, from `scripts/release-notes.mjs`: a `### <pull request title> (#N)` heading per change, its description below, and in the change log a `## vX.Y (date)` heading per version. Entries titled "Change log through vX" regenerate the change log and are left out; notes with no such headings are one entry titled "Release notes".
- The update notice shows in `app` and `clone` modes while `available` is true. **Later** stores the version in this browser (`ade-update-later` in local storage); a newer `latest` shows the notice again. During an install it follows the same flow as Settings, one poll for the page, and reloads once `/api/version` reports the new version.
- The notice after an update compares the running version with the last one this browser saw (`ade-seen-version`). A first visit records it and shows nothing; a newer version shows the entries from `GET /api/changelog?after=<last seen>` once, and records the new one. Hosted deployments do not show it. With `reopen` set (the update changed the app's window), the notice has **Reopen now**, which sends `relaunch`. An install or rollback started on the page stores its version in session storage (`ade-reopen-after-update`) before the reload; the page that loads on that version sends `relaunch` at once without recording the version, so the reopened window announces it. An install the server started while idle does not reopen on its own.
- What's new is a page of Help (`#view=help:whats-new`), also opened from the footer's version panel and Settings, Updates. It shows the first ten versions, and **Show older versions** adds twenty at a time.
- About is a page of Help too (`#view=help:about`), at the foot of its list and opened from the footer's version panel: the version and commit from `GET /api/version`, the license, the source repository, GUFI, and that ACTIVATE Studio is built and maintained by Parallel Works. It names ACTIVATE Studio whatever the deployment is called.
- `CHANGELOG.md` ships in the macOS app (`Contents/Resources/app`, checked by `deploy/mac/check_app.sh`), the workflow bundle (`deploy/make_bundle.sh`), and the container image (`deploy/app.def`, whose smoke test asks `/api/changelog` for it).

## AI features

The `aiEnabled` setting (`PUT /api/settings {aiEnabled}`; the client config carries it) is on unless a deployment sets `AI_ENABLED=0` or saves it off. Off:

- Chat and Agents leave the sidebar, and a link to either opens the first page shown. The wizard and Settings also take them out of the `sections` setting, and put them back when AI features are turned on; their switches under Sidebar are disabled meanwhile.
- The footer drops its model line.
- `POST /api/chat/stream` answers "AI features are off in this Studio." as the reply's text and ends, without calling a model or recording the turn. `GET /api/chat/models` lists no models, with that message as `error`; `GET /api/ai/health` answers `status: "off"`; `/v1` refuses with 403; `POST /api/kb/label-suggestions` refuses with 409; indexing captions no images.
- Search, the library, query, statistics, history and the MCP endpoint are unchanged.

With sign-in off the personal model key routes act for the one user, and their answers carry `single: true`: `GET /api/me/model-key` reports the key (`mode`, `last4`, `baseUrl`), `POST /api/me/model-key {key, baseUrl, endpoint}` saves it, `POST /api/me/model-key/clear` removes it, and `POST /api/me/model-key/test {key, baseUrl, endpoint, model, tools}` asks the endpoint's `/models` (see Endpoint options under Model access for `endpoint`, `model` and `tools`). The test answers `status` `ok` with `models` and the model `ids` (at most 500), `ok` with `models: 0` for an endpoint that offers none, `auth` for a refused key, or `unreachable` with a `message`, and a base URL that is not http(s) is a 400. A 404 sets `notFound` to the URL tried, and the message names it and says what to do: on the ACTIVATE gateway path (`…/api/openai/v1`), that the host is not an ACTIVATE platform and an OpenAI-compatible service goes under OpenAI-compatible endpoint; on a base URL that ends in `/chat/completions` or `/models`, the base URL without it; on one that already ends in a version such as `/v1`, that the endpoint may not list its models and model names can be typed under Advanced; on anything else, the same address with `/v1`. The key is kept in the vault beside the index (`user-credentials.json`), encrypted with the `.credentials-secret` beside it, since there is no sign-in to tie a browser cookie to; the startup scrub of personal entries keeps it while sign-in is off. A request without a user then uses it wherever a user's key is used: chat, the model listing, the footer's health check, and label suggestions. With sign-in on, or with `DISABLE_PERSONAL_KEYS=1`, nothing changes. The wizard saves the default model it offers as `ragDefaultModel`, the default for label suggestions and the grounded model, and as the chat's remembered model in the browser (`aiChat.model`).

Settings, General has the AI features switch on its AI features tab, which saves as it is switched, beside the mission, the suggested questions and the captioning model. Settings, Model access appears on a single-user install for the endpoint.

## Model access

Model calls and platform calls take their credential in this order. Models: the person's own key or endpoint, a key someone shared with the deployment, `PW_API_KEY`, then the pw CLI. Platform calls (the Workflows page, the DAG viewer, the assistant's platform tools, sessions): the person's own platform key (one saved without a base URL), then the same chain. With sign-in off, a platform key saved under Model access now reaches the Workflows page and sessions as it reaches chat; before, those used the pw CLI regardless.

The pw CLI's credential comes from a context in its credential file, `~/.config/pw/credentials`, or `$PW_CREDENTIALS_DIR/credentials` as the CLI reads it. With no choice made, the Studio follows the CLI: `PW_CONTEXT` as the server was started with, else the file's current context. A context chosen in Settings is saved as `pwContext` in `access.json` beside the index. Either way the choice applies in two places: the gateway (`GATEWAY_BASE`) moves to the context's platform, `https://<server>/api/openai/v1`, unless `PW_GATEWAY_URL` or `OPENAI_BASE_URL` fixes it; and `PW_CONTEXT` is set in the server's environment, so every `pw` command it runs uses the same context. The credential is the context's API key or token from the file. A context made by `pw auth login` holds an access token the CLI renews: within two minutes of its expiry, or when the file holds no token (the CLI keeps it in the operating system's credential store), the Studio runs `pw auth token --print -o json --context <name>`, without `PW_API_KEY` in its environment, and uses the token it prints until `expires_in` runs out. Requests that can wait (the model list, the health check, a chat turn, the Workflows routes, the platform API) wait for the renewal, at most 5 to 15 seconds; others use the current token and the renewal finishes in the background. A renewal that fails for lack of network is not retried for 30 seconds. The Studio never renews a token itself and never sends one to the browser. A change of model access dispatches `ade:model-access-changed` in the page, which the chat, the footer and the app configuration (whether the Workflows page shows) read again; before, the Workflows page appeared only after a reload.

- `GET /api/access`: `single`, `models` and `platform` (each `source`: `endpoint`, `key`, `shared`, `env`, `cli`, `sidecar` or `none`, with `host`, `context`, and for a stored key or endpoint `baseUrl`, `last4`, `kind`), `deployment` (what requests fall back to without a key of the person's own), `gatewayHost`, `platformOrigin`, and with sign-in off `cli` (`available`, `version`, `path` and `source` for where the CLI runs from, `chosenPath`, `commonDirs`, `contexts`, `chosen`, `active`, `used`, `gatewayFromEnv`, `envKey`) and `login`. `?fresh=1` looks for the CLI again at once. Each context has `name`, `server`, `organization`, `kind` (`sign-in`, `api-key`, `token`, or null when the file holds no credential), `expiresAt` and `expired` for a platform token, `current`, and `renewError`. With sign-in on, `cli` is null and a `cli` source names its host only: the CLI's contexts are the deployment's.
- `PUT /api/access/source {context, clearKey}`: chooses a context, or `null` to follow the CLI. `clearKey` also removes the stored key or endpoint, which would otherwise keep taking precedence. Sign-in off only (403 otherwise); an unknown context is a 400.
- `PUT /api/access/cli/path {path}`: where the pw CLI is, as a full path, when the Studio does not find it; `null` forgets it. It is kept in `INDEX_BASE/pw-cli.json` and refused (400) unless the program answers `--version` as the CLI does. Every pw CLI call runs the program found in this order: `PW_CLI` (a path, taken as it is even when nothing is there, or a name looked up on `PATH`), the chosen location, `pw` on `PATH`, then `~/.local/bin`, `~/bin`, `~/pw`, `/opt/homebrew/bin`, `/usr/local/bin` and `/usr/bin`. It is looked for again whenever Model access loads and after a call fails because the program is gone. Sign-in off only.
- `POST /api/access/cli/login {host}`: runs `pw auth login --device <host>` and answers once the CLI prints its address and code: `login` with `host`, `state` (`starting`, `waiting`, `done`, `failed`, `canceled`), `url`, `code`, `context` and `message`. `GET /api/access/cli/login` reports it, and `POST /api/access/cli/login/cancel` stops the CLI. A host may be typed as a URL. On success the CLI saves the context and makes it current; a Studio following the CLI uses it from then on, and one pinned to a context is moved to it. The code expires after ten minutes. Sign-in off only.

The device flow belongs to the pw CLI. The platform's device authorization endpoint (RFC 8628, `/api/oidc/device_authorization`) is documented for the pw CLI's own client; another client ID is refused with `invalid_client`, and dynamic client registration (`/api/oidc/register`) takes an initial access token the platform issues to its own workloads. An application an organization administrator registers (`/api/organizations/<org>/oidc/apps`) signs people in, and its access token is not documented to reach the platform API or the model gateway. The Studio therefore runs the CLI for the sign-in.

### Endpoint options

An OpenAI-compatible endpoint saved under Model access can carry options for portals that differ from the OpenAI shape, sent as `endpoint` with the key: `auth`, the header the key goes in (`bearer`, the default, sends `Authorization: Bearer <key>`; `api-key` and `x-api-key` send the key as that header; `none` sends no key); `headers`, extra headers as `{name, value}`; `models`, model names for an endpoint that lists none; and `query`, a query string without the `?`, appended to every request. Header names must be HTTP tokens, values one line; `Host`, `Content-Type`, `Content-Length`, `Connection`, `Transfer-Encoding`, `Accept-Encoding` and `X-Allocation` are refused, as is a header named like the one the key already goes in (choose `none` to send `Authorization` yourself). At most 20 headers and 100 model names.

They are stored with the key and protected the same way: in the vault, encrypted with the vault's secret (`opts`, beside `blob`), with sign-in off; in memory and inside the sealed key cookie with sign-in on. They never reach the browser: `GET /api/me/model-key` and the save answer `endpoint` as `{auth, headers, models, query}` with header names only, and they are never logged. A save or test with no key keeps the stored key, for the endpoint it was stored for only; a header sent with a name and no value keeps its stored value; `endpoint` left out keeps the stored options for the same endpoint. A test with no key against another address is a 400, and the stored key is not sent there. A platform key (no base URL) carries no options.

Every request the Studio makes to the endpoint carries them: the model listing (`/api/chat/models`, Settings, label suggestions), the health check (`/api/ai/health` and the key test), chat turns, label suggestions, the tool check, and the OpenAI-compatible endpoint at `/v1`, which for a signed-in caller without a bearer key now forwards to that person's endpoint (`studio-rag` passthrough, `studio-agent` turns, `/v1/models?all=1`, and the default model for a bare `studio-agent`) instead of sending the endpoint's key to the gateway. The gateway's provider probes are not run for an endpoint, and its key is never given to platform tools. Image captioning in indexing uses the deployment gateway (`PW_GATEWAY_URL`, `PW_API_KEY`), not a personal endpoint, and is unchanged.

With `models` set, nothing asks for a model list: the names are the listing, and the health check is a streamed chat completion with the first name, read to its first frame and kept for five minutes (dropped on Re-check and on a test), since the footer asks every minute. The test answers `checked: "completion"` then, and `"models"` otherwise.

After a test that answers `ok`, one more chat completion checks tool calling and the answer carries `toolCheck: {model, result, message}`. The model is `model` from the request when the endpoint lists it (the page sends the chat's remembered model), else `ragDefaultModel` when listed, else the first id that does not look like an embedding, speech or image model. The request offers one tool, `get_utc_time`, with a prompt that needs it, `max_tokens` 256 (dropped and retried once if the provider refuses a token cap), and a 15 second limit; it streams or not as chat would for that model (`CHAT_NO_STREAM`) and carries its `chatTemplateKwargs`. `result` is `calls`; `no-call` when the model answered without calling it, with a note when it wrote the call as text, which is what a server that does not parse tool calls for the model passes through; `refused` when the endpoint turned the request down over the tool (vLLM without `--enable-auto-tool-choice` and a `--tool-call-parser`, or an Ollama model without tool support, say), which chat would hit on every turn; `failed` when the check did not complete, including a reasoning model that spent the whole cap; or `emulated` for a model named in `CHAT_SYSTEM_IN_USER`, which chat drives through prompt-level tool emulation (`emulatedPrompt`: the tools in the prompt as a JSON envelope, and a library search run before the first turn), so its own tool calling is not asked. Nothing is refused on the result. `tools: false` skips the check; the API key tab uses it when it asks a host's `/v1` after the platform path answered 404.

### Subscriptions through ACTIVATE

ACTIVATE connects a ChatGPT plan (the `codex-subscription` integration) and GitHub Copilot (`github-copilot`) as personal AI providers, and serves their models through its gateway as `me:<provider>/<model>`. The Studio relays the platform's own flows with the person's own platform credential: their platform key, or with sign-in off whatever the Studio runs with; never the deployment's credential on a shared deployment.

- `GET /api/access/subscriptions`: `available` (false, with `reason`, without a platform credential of the person's own), `user`, `org`, `codex` (`offered`, `providers`), and `copilot` (`offered`, `providers`, `github`: `linked`, `username`, `appConfigured`, `tokensAllowed`). It reads `/api/auth/whoami`, `/api/auth/whoami/organization`, `/api/organizations/<org>/ai-integrations`, the person's AI providers, and `/api/integrations/github/oauth/status`.
- `POST /api/access/codex {name, reconnect}` starts the platform's ChatGPT device sign-in (`/api/organizations/<org>/users/<user>/codex-device-authorizations`) and answers `id`, `url`, `code`, `expiresAt` and `intervalSec`; `POST /api/access/codex/<id>` asks how it stands, `pending` or `connected` with the provider. The name keeps lowercase letters and digits, as the platform requires.
- `POST /api/access/copilot {name}` adds a provider from the platform's `github-copilot` entry. It uses the GitHub account linked to the person's ACTIVATE account, which is linked on the platform; the Studio does not link one.

The Studio does not sign in to OpenAI or GitHub itself. A ChatGPT plan is not offered to third-party applications through OAuth, and Copilot's device flow is GitHub's own client; using another product's client ID would break its terms. GitHub Models is the supported way to use a GitHub account's models directly: a fine-grained personal access token with the Models (read) permission, as an endpoint at `https://models.github.ai/inference`, whose model list the Studio reads from `https://models.github.ai/catalog/models`.

## Working offline

The Studio tells a network failure (`ENOTFOUND`, `EAI_AGAIN`, `ECONNRESET`, `ECONNREFUSED`, `ETIMEDOUT`, `ENETUNREACH`, `EHOSTUNREACH`, undici's connect and socket errors, a timeout, or the pw CLI's "no such host", "connection refused", "i/o timeout" and the like) from any other failure, and reports it as "Could not reach <host> (<code>). This computer may be offline, or the server is down." with no wait beyond a short timeout:

- The model list (`GET /api/chat/models`) answers 200 with that sentence as `error` and `offline: true`, and still lists a model served beside the Studio. `GET /api/ai/health` answers `status: "offline"`, which the footer shows as **offline**. A reply through an unreachable gateway ends with the sentence. The model listing waits at most 10 seconds.
- An endpoint on this computer (`http://127.0.0.1:<port>/v1`) needs no network: the model list, health check and replies go to it alone. One that does not answer reads "Nothing answers at 127.0.0.1:<port> (ECONNREFUSED). Start the model server on this computer, or check its address." with `status: "unreachable"`, since the network has no part in it.
- The update check answers `offline: true` with `state: "idle"` and no `error`, and checks again in 5 minutes instead of 15; Settings, Updates shows **Offline; the Studio checks again later**. A download that loses its connection still fails as an error, and says to try again once online.
- Attached MCP servers are listed with a 5 second limit per step, so an unreachable one costs a chat turn a few seconds once a minute at most, and reads "Could not reach <host> (<code>)." in Settings.
- Before a pw command, the Workflows routes ask whether the platform answers at all (a `HEAD` of its address, 4 second limit, kept 30 seconds, 10 when down). When it does not, they answer 503 with the sentence at once instead of waiting out the CLI's own timeout of a minute or more. A pw command that fails for the network answers 503 the same way.

## Certificates and proxies

Outbound HTTPS from the server (the update check and download, model providers and gateways, the platform API, attached MCP servers) works on a network that inspects TLS with its own certificate authority, and through a proxy.

- The server's first import (`server/src/netStart.ts`, from `netTrust.ts`) adds the system's trusted certificates to Node's own list with `tls.setDefaultCACertificates`: the set `node --use-system-ca` reads, which on macOS is the keychains' trusted roots (user, administrator and system trust settings, so one installed by the Mac's management counts) and on Linux the system bundle (`SSL_CERT_FILE` and OpenSSL's default paths). Certificates named by `NODE_EXTRA_CA_CERTS` stay. `STUDIO_SYSTEM_CA=0` leaves Node's own list alone. It is done at runtime rather than with a Node flag, so the macOS app, the container and a clone get it the same way.
- With `HTTPS_PROXY` or `HTTP_PROXY` (either case) set, the server routes its requests through it with `http.setGlobalProxyFromEnv`, which covers `fetch` and `https.request`. `localhost`, `127.0.0.1` and `::1` are added to `NO_PROXY` (and `no_proxy`), so models and the platform on this computer go direct. A user name and password in the proxy address are sent as Basic sign-in.
- The macOS app's run loop reads the system proxy (`scutil --proxy`: the web and secure web proxies and the exceptions list) before each start when `studio.env` sets no proxy, and exports `HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY`. A PAC file is not followed; the log names it. `studio-run.sh --system-proxy` prints what it would set.
- The server logs one line at start: "outbound HTTPS trusts the system's certificates (<n>) as well as Node's own", then the proxy and its exceptions when there is one.
- A refused certificate reads "The connection to <host> used a certificate this computer does not trust (<reason>). If your network inspects HTTPS, its certificate authority has to be trusted by macOS (in Keychain Access, or installed by the Mac's management); the Studio uses the system's trusted certificates." (worded for Linux and Windows on those), with separate sentences for an expired certificate and one for another name (`net.ts`, `trustMessage`).
- A proxy that cannot be reached reads "The proxy at <host:port> could not be reached (<code>), so <host> could not be either.", and one that refuses the tunnel "The proxy at <host:port> would not open a connection to <host> (it answered <status>).", or for 407 that it asks for a sign-in (`proxyMessage`).
- Neither is taken for being offline: the update check answers `state: "error"` with the sentence and `offline: false`, the model list and health check `status: "unreachable"`, and the platform routes 503 with the sentence.
- Not covered: image descriptions, which `indexer/enrich.py` asks the gateway for with Python's `urllib` when AI features and a vision model are on, use Python's own certificate list and follow `HTTPS_PROXY` themselves.

## Settings, General

General is a page of tabs, each with an address of its own: `#view=settings:appearance`, `branding`, `sidebar`, `ai`, `indexing`, `updates` and `server`. `#view=settings:general` opens Appearance, and the update notice and the footer's update link open `#view=settings:updates`. Updates is left out where a Studio has none (hosted). Appearance (the theme, accent and surface tone), the icon, the sidebar switches and the AI features switch save as they change; Branding, AI features and Indexing have Save settings for their other fields. Server shows the port the Studio and its MCP endpoint share: in the macOS app a new one is saved for the launcher and applied by a restart, and elsewhere it names the `PORT` variable to set.

## Using it from other tools

The deployment serves an OpenAI-compatible endpoint with two models:

| Model | Does | Suits |
|---|---|---|
| `studio-agent` | runs the full assistant and returns a finished answer with citations | tool-calling clients such as pw code |
| `studio-rag` | adds retrieved, cited context to one fast model call | plain chat clients and scripted questions |

Settings, "External access" chooses which of the two appear in model lists (`studio-agent` by default); both can be called by name either way. `studio-agent/<model id>` pins the underlying model for a request. The same section can publish the endpoint into the platform's chat and provider catalog, shows the registration state and the exact model ids, and logs recent calls with the model used, the credential, the retrieval terms, and the timing. The MCP endpoint and the command to add it to pw code are there too. Inside the Studio's own chat the published models are hidden, since the chat already has the same grounding.
