# Setting up your studio

Every deployment-specific choice lives in environment variables, conventionally in a gitignored `.env` at the repo root. Copy `.env.example` to `.env`, adjust, and restart. Nothing brand- or site-specific belongs in the code.

## Point it at your corpus

`KB_ROOT` is the directory the studio works over; `KB_LABEL` is the human name shown at the top of the library tree and in the help page. Build the index once with `indexer/setup_gufi.sh` (toolchain) and `KB_ROOT=... indexer/reindex.sh` (index, extraction, embeddings). After that the background sync keeps the index current; `SWEEP_INTERVAL_SEC` sets the cadence.

## Name and brand

`APP_NAME` is the product name in the header and the browser tab. `APP_ICON` points at an image (PNG or SVG works) shown beside it, either an `https://` URL or a path on the resource; without one, a letter badge from the first character of the name appears instead, and the empty chat shows the Studio's own mark above its greeting. `APP_FAVICON` points at an image used as the browser tab icon; it falls back to `APP_ICON`, and with neither set the tab shows the generic bundled favicon. `THEME` picks the default of light or dark (light follows a device set to dark); every user can toggle from the sidebar footer or choose Light, Dark or System in Settings, General, Appearance, and their choice persists in the browser.

## Chat

The assistant talks to any OpenAI-compatible endpoint: set `OPENAI_BASE_URL` and `OPENAI_API_KEY`. On the ACTIVATE platform with an authenticated pw CLI, leave both unset and the platform gateway is used with no configuration. `SUGGESTED_PROMPTS` (a JSON array) fills the suggested questions on the empty chat; write prompts that fit your corpus. `KB_MISSION` is the mission and context the assistant treats as authoritative. A single-user install (sign-in off, not deployed by the platform) has defaults for both written for one person's own files. `ADE_VISION_MODEL` names a vision-capable model and turns on image captioning during indexing, which makes images findable by what they depict; Settings, General sets it too (AI features), and its Indexing tab holds the other choices of what indexing reads and how many threads it uses.

`CHAT_ENGINE` chooses what answers chat. `auto`, the default, has pw code answer where the Studio runs under ACTIVATE (the platform is connected and a platform credential is present) and a pw code daemon can be reached, and the Studio assistant elsewhere; `pwcode` and `studio` choose one. A Studio run on its own, with any OpenAI-compatible model endpoint and no ACTIVATE, works as before: the Studio assistant answers, the pw code daemon is never asked, the chat bar shows no engine choice, and Settings shows no pw code settings unless `CHAT_ENGINE` is set to `pwcode`. `PWCODE_MODEL` names the model new pw code chats start with, and empty uses pw code's default. `PWCODE_PERMISSION_MODE` sets what they may do without asking: `read-only`, `accept-edits`, `auto` or `plan`, or empty for pw code's default, which accepts edits and asks before commands. Bypassing permissions is not offered. Settings, External access, "What answers in chat" sets all three, and people choose for each chat in the chat bar.

`CLAUDE_CODE_ACCOUNTS` decides whether pw code may run on Anthropic's models through Claude Code accounts: `on`, `off`, or `auto`, the default. Auto is on for a single-user install (sign-in off, not deployed by the platform) and off on a Studio where people sign in or that the platform deployed, such as one launched by the ACTIVATE workflow, since the people it serves may not use Anthropic. Someone whose own pw code already had Claude Code accounts when the Studio first looked keeps them: the Studio asks their pw code once when it reaches it and records them in `claude-code-in-use.json` beside the index, so nobody loses access without being told. Off, nothing in the Studio offers them: Settings, Accounts shows no Claude Code accounts row, the machine records the Studio passes to the pw code chat and the Code page say Claude Code is not allowed (so their model pickers list no Claude models and no account panel), and the server refuses (403) the account routes, a session started on a `claude-code/` model or a Claude account, a switch to one (settings, `/model`, `/claude-code`), and a session pw code starts on such a model by its own default, which it archives. An administrator can change it under Settings, External access, **Claude Code accounts**; on a Studio with sign-in only its administrators can (the deployment's owner, `PW_USER`, and `STUDIO_ADMINS`), as for the main library. A saved choice wins over the variable.

A pw code chat session gets the Studio's own tools through the Studio's MCP server, with a token sealed for that person and conversation, whether or not MCP is turned on for other clients: search and statistics from the index across the libraries, reading and writing library files (reports as PDF, Word or Excel included), labels, transfer locations and status, platform workflows where the platform is connected, and the deployment's own tools, skills and attached MCP servers' tools. Each call runs as the Studio assistant's would, in the chat's scope, with the person's own key, and only for the kinds of tools they left on under +, then Tools. The tools that only read run without asking in every permission mode; the others ask as the mode decides. Deletes, cluster changes and transfers wait for an answer in the Studio's own chat, so a pw code chat does not get them, nor the agent tools. Before each message the Studio reads the session's MCP servers from the daemon, reconnects the studio server once when it failed or lists other tools, and otherwise starts a new session. The session reaches the server at `127.0.0.1` on the Studio's port, or at the one address `HOST` names; for a daemon on another machine the Studio also tries this machine's host name. `STUDIO_MCP_URL` sets the address instead, for a server behind a container's port mapping or a proxy. A pw code session of a person's on another machine reaches the same tools as them once they add the Studio to pw code there through the session proxy (HELP, Code; REFERENCE); `STUDIO_SELF_URL`, the Studio's address on the platform, names that address in the command the chat's setup card shows where the Studio cannot tell it from the proxy's headers. When no address works, the Studio assistant answers that message, the chat says why, and the Studio assistant answers by default for ten minutes.

The chat greeting uses `APP_USER_NAME` in standalone mode. Behind the platform, a verified JWT identity takes precedence (below).

## Readers for other file types

Indexing reads PDFs, Office and OpenDocument files, text and images. A reader for another format, or one to use in place of a built-in reader, is a command listed in `$INDEX_BASE/extractors.json`; set `STUDIO_EXTRACTORS` to a file path to use another file, and `studio-server extract --extractors FILE` takes precedence over both. Nothing else needs to change, and there is no setting for it in the UI.

```json
{"extractors": [
  {"name": "dwg", "suffixes": [".dwg", ".dxf"], "command": ["/opt/tools/dwg2text", "--plain", "{path}"], "timeoutSeconds": 300}
]}
```

The contract: `{path}` in any argument is replaced by the file's absolute path, or the path is appended when no argument has it; no shell is involved. stdin is empty, the working directory is a scratch directory removed afterwards, and the environment is the Studio's plus `OMP_THREAD_LIMIT=1`. Exit status 0 with text on stdout is the file's text (UTF-8, invalid bytes replaced, `\r\n` read as `\n`, the usual length cap). Exit 0 with only whitespace means the file has no text; any other status is a failure, and in both cases nothing is cached, so the next pass tries again, and the start of stderr goes to the index log. The command and its process group are stopped after `timeoutSeconds` (120 when absent, at most 3600). Suffixes are matched without regard to case; the plain text formats cannot be taken over. A missing `extractors.json` is ignored; a broken one is logged and the pass goes on without it. A file named by `STUDIO_EXTRACTORS` or `--extractors` has to exist and parse, or the pass exits with status 2.

## Tools, skills, and agent files

The assistant's tool set is managed from the Settings page and from files.

- Built-in tools live in the server (`server/src/chat/tools.ts`). Settings lists each one with an on/off toggle; clicking a tool's name shows its exact call specification, which you can copy as a starting point for your own.
- Custom tools defined in Settings are saved with the runtime settings (`index/settings.json`). Each is a name, a description for the model, and a command; the command runs on the Studio server and its output returns to the conversation. On a Studio with sign-in only its administrators (`PW_USER` and `STUDIO_ADMINS`) save them, and a tool runs only as an administrator last saved it: the save keeps a digest of the list beside it (`customToolsApproved`), and a list that does not match, written by an older release or by hand, is neither offered nor run until an administrator saves Settings again. Attached MCP servers are HTTP(S) addresses only; the Studio starts no stdio MCP server from its settings.
- File-based extensions load from `index/extensions/` and take effect without a restart. On first start, when that directory does not exist yet, the server seeds it from the repository's `extensions-starter/` set (two example tools, three skills, and an inactive persona template), so a fresh deployment has working examples to copy; delete or edit them freely, they are never re-created once the directory exists:
  - `tools/*.json`, each `{ "name", "description", "command" }`, behave like custom tools.
  - `skills/*.md` are instruction sets the assistant loads on demand through the `use_skill` tool, either when the user names one or when the task matches the skill's frontmatter description.
  - `agents/default.md` is appended to the system prompt on every request, as the deployment's standing instructions.

Commands run with the server's user and environment. Treat tool and skill files as configuration with shell access, and keep the extensions directory outside version control (the default location is beside the index, which is already ignored).

A tool the assistant calls with arguments receives them as positional parameters (`"$@"`), not as text pasted onto the end of the command line. Quoting groups words, so `--path "two words"` arrives as two arguments; everything else is literal, so a semicolon, a pipe, backticks, or `$(...)` in a model-written argument is passed to the command as data and never interpreted by the shell. Write commands that expect `"$1"` and friends. This matters most when the assistant is reasoning over retrieved documents, since those are the untrusted input that could otherwise try to steer an argument.

## Help content

The in-app Help page renders `docs/HELP.md`: the text before the first heading is the Overview, each `##` heading is a page, and a `#` heading groups the pages after it in the rail. The guide calls the app Studio, its default name, so it reads the same on GitHub; a deployment given another product name shows that name in place of the word, except in "ACTIVATE Studio" and in code. `<!-- kbLabel -->` becomes a line naming the knowledge base, and the older `{appName}` and `{kbLabel}` placeholders are still filled in. Point `HELP_FILE` at your own markdown to replace it entirely.

## Platform identity (optional)

When served behind the ACTIVATE platform, the session proxy forwards a short-lived (5 minute) RS256 JWT in the `X-PW-User-Token` header: `sub` is `user:<username>`, `iss` is `pw-session-proxy`, and `aud` carries `session:<sessionId>` and `session:<owner>/<sessionName>`. It identifies the user and proves the platform forwarded the request; it carries no credentials. Set `AUTH_JWKS_URL` to the platform's keys endpoint (`https://<platform-host>/api/platform/keys`, the `jwks_uri` from its OIDC discovery document) to verify it; `AUTH_HEADER` names the header (default `x-pw-user-token`), and `AUTH_ISSUER`/`AUTH_AUDIENCE` add the standard claim checks, with `session:<owner>/<sessionName>` the natural audience to pin. With `AUTH_REQUIRED=1`, API requests without a valid token are rejected; without it, verification is best-effort and the verified identity simply personalizes the app. Role-based permissions (who can manage the library versus only chat) are a planned layer on top of this identity.


A Studio can also sign people in itself, through ACTIVATE's OpenID Connect provider or any other: set `OIDC_ISSUER`, `OIDC_CLIENT_ID` and `OIDC_CLIENT_SECRET`. A request with a valid proxy JWT is that user; otherwise the sign-in session decides, and both turn on everything below that says "identity verification enabled". Configuration and the ACTIVATE registration steps are in [`DEPLOY.md`](DEPLOY.md), Sign-in.

## Per-user model keys (shared ACTIVATE sessions)

With identity verification enabled, each user can add their own model API key under Settings, "Accounts". Their chat model calls, model listing, health checks, and platform CLI tool executions then run on their key. Users without one of their own get no ACTIVATE credential: the deployment credential is never lent to a person. Their chat can use an OpenAI-compatible endpoint the administrator sets for everyone (`OPENAI_BASE_URL` and `OPENAI_API_KEY`, naming a gateway that is not an ACTIVATE platform's) or the sidecar model (`SIDECAR_MODEL_URL`). This surface only appears when `AUTH_JWKS_URL` is configured; a standalone single-user deployment never shows it and never creates the credential files.

Storage and trust, stated plainly: keys are held server-side (browser storage is unreliable inside the platform iframe and the calls are made by the server anyway), either encrypted at rest in `<index>/user-credentials.json` with a locally generated `<index>/.credentials-secret` (both written mode 0600, both outside the repository), or, with "remember" unchecked, in server memory only with a 12 hour expiry. Encryption at rest protects the files, not the running process: a key added here is necessarily available to the server and its operator, so users should prefer a key they can revoke. Key material never goes to the browser (status APIs return only the last four characters), never appears in logs, and never appears in error messages. The platform's delegated-credential flow, when available, replaces this mechanism without changing any call sites.

## Labels

Files and directory subtrees can be labeled from the library (select with ctrl or cmd click, then Labels). Labels are stored as extended attributes on the files themselves and indexed by GUFI, so they survive copies and are visible to any xattr-aware tool. A label on a directory applies to everything beneath it. The chat surfaces labels on retrieved material and can filter by them; use labels for provenance distinctions such as research versus validated.

## RAG endpoint (OpenAI-compatible /v1)

The server exposes an OpenAI-compatible surface at `/v1` (`/v1/models`, `/v1/chat/completions`), so any OpenAI-speaking client can use the knowledge base as a grounded model. Two virtual model families: `studio-agent[/<gateway-model-id>]` runs the full assistant pipeline (system prompt and the retrieval tool loop) on the underlying model and returns the grounded answer; `studio-rag[/<gateway-model-id>]` injects retrieved, citation-numbered context blocks and makes a single model call; it is unlisted in `/v1/models` by default (agent clients driving it with their own tools lose the grounding) but stays callable by name; the Settings RAG section has per-model advertise options (`RAG_ADVERTISE_RAG_MODEL=1` lists studio-rag, `RAG_ADVERTISE_AGENT_MODEL=0` hides studio-agent), and `?all=1` always lists both. Advertise studio-agent where users drive tool-calling harnesses, studio-rag where a plain chat interface wants fast grounded answers. Any other model id behaves like studio-rag with that model. The bare forms use the default model set on the Settings RAG endpoint section.

Callers authenticate with their own gateway API key as the bearer token; the endpoint holds no credentials and simply forwards the caller's key, so per-user credential state (including keys that need periodic unlocking) passes through. The "allow deployment credential" setting opts callers without a key onto the deployment's own credential. Per-request headers: `X-RAG-Top-K` (1 to 20), `X-RAG-Tags` (comma-separated label filter, inheritance respected), `X-RAG-Off: 1` (plain passthrough). Retrieval fails open by default (`RAG_FAIL_OPEN=false` makes retrieval errors hard failures).

The Settings RAG endpoint section can also register the surface into the platform's chat and AI provider catalog (a managed `pw endpoints run --openai` child process around a local forwarder; requires an authenticated pw CLI on the host). The registered model appears as `session:<owner>:<name>-rag/studio-agent` and is callable through the platform gateway like any other model, which is how pw code consumes it. Platform callers reach it with their own credentials; the forwarder injects the deployment credential only for keyless clients such as pw code. Enable "register automatically at startup" to survive restarts.

## Deployment postures

The application runs in one of three postures; state the choice deliberately rather than inheriting it.

*Single user* (the default, and the right shape for on-premises or air-gapped deployments): leave `AUTH_JWKS_URL` unset. There is no identity layer, the personal-key surface never appears, the per-user credential store is never created, and the deployment credential is simply the operator's own. Point `OPENAI_BASE_URL` (or `PW_GATEWAY_URL`) at any OpenAI-compatible endpoint, including a local vLLM or llama.cpp server; indexing, embeddings (local GGUF model), and OCR are already local, so nothing requires outbound network. Disable or localize the vision-captioning model for fully disconnected operation.

With no identity layer, the server answers anyone who reaches its port, and everything it does runs on the operator's credential: chat and platform tools, queries on the operator's cluster libraries, and agents on this host. It listens on all interfaces (`HOST=0.0.0.0`) by default, so run it where only the operator can reach it, behind the platform's session proxy or a host firewall, or set `HOST=127.0.0.1` on a workstation.

*Multi-user, shared credential*: identity verification on (`AUTH_JWKS_URL`), and `DISABLE_PERSONAL_KEYS=1`. Users are identified, no ACTIVATE part runs for them (the deployment credential is never lent to a person), and models come from an endpoint the administrator sets for everyone or the sidecar; the server provably collects no user keys (the flag is env-only by design, so no UI setting can re-enable collection).

*Multi-user, personal keys*: identity verification on, personal keys enabled (optionally `REQUIRE_PERSONAL_KEY=1` to refuse the administrator's endpoint and the sidecar for chat). Each user's calls run on their own key, which is the correct posture for per-user model entitlements and keys that need periodic unlocking. This is the posture that custodies secrets: keys are encrypted at rest but visible to the server process and its operator, as described above. The platform's delegated-credential flow, when available, replaces the custody entirely.

`REQUIRE_PERSONAL_KEY` and `DISABLE_PERSONAL_KEYS` together would be contradictory; when both are set, the disable flag wins and the requirement is ignored. The ACTIVATE deployment workflow exposes these postures as a dropdown at launch. Its multi-user postures also set `AUTH_REQUIRED=1`, so every request must carry a verified session; personal spaces need that. Since the workflow cannot then ask for the first index over HTTP, it leaves `index-on-launch` in the index base, which the server takes once as it starts and answers with a full index.
